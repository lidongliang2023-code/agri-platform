# 主数据后端可用性审计（2026-10-12）

## 0. 这份文档回答什么问题

前端页面拿不到真数据，可能是"前端写错了"，也可能是"后端根本调不通"。
本文用**实测**把两类原因分开，并给出每一处的证据与修法。

审计口径：主数据后端（`:8083`）在**已通过平台 SSO 拿到合法访问令牌**的前提下，
逐个调用 PRD V2.0 里 `/admin/masterdata/*` 的只读端点，统计业务码。

## 2. 本轮已修（有实测为证）

### 2.1 认证链路：平台令牌到不了主数据（根因，已修）

- 现象：SSO 登录成功、`core-platform` 认这枚令牌（`/api/v1/auth/me` 200），
  但同一枚令牌打 `/admin/masterdata/dashboard` 返回 `{"code":2005,"message":"Token无效"}`。
- 根因：主数据后端有**一整套私有令牌体系**——`jwt.secret=agri-masterdata-jwt-secret-key-2024`、
  issuer 私有，且 `TokenService.validateToken` 要求令牌**必须存在于自己的 Redis** 里。
  平台令牌是无可状态 JWT，永远不会在它的 Redis 里，于是必然被判无效。
- 修法：新增 `PlatformJwtProperties`（读 `agri.jwt.*`，与 core-platform 同键）+ `PlatformTokenService`
  （HS256 验签 + 校验 issuer + 读 `sub/username/roles`），`AuthenticationInterceptor` 先判平台令牌、
  再回落私有令牌（存量 `/api/*` 族的迁移窗口）。业务侧读身份的 `SecurityUtils.*` 一行未改。
- 实测：同一枚 SSO 令牌，修复前 `2005`，修复后 `/admin/masterdata/dashboard` 返回
  `code=200` 且带真实 `coreMetrics`。

### 2.2 平台级编译开关缺失（已修，影响全部卫星模块）

- 现象：认证打通后 `/admin/masterdata/dashboard` 立刻 500，
  堆栈 `IllegalArgumentException: Name for argument of type [java.lang.String] not specified ...
  Ensure that the compiler uses the '-parameters' flag.`
- 根因：Spring Framework 6.1（Boot 3.2）已移除从调试信息猜参数名的能力。
  `core-platform/pom.xml` 自己设了 `<parameters>true</parameters>`，而根 `pom.xml`
  （11 个卫星模块的父 POM）没有 → 卫星模块里所有写成 `@RequestParam String x`、
  `@PathVariable Long id`（未显式写名字）的接口**运行时必 500**。
- 修法：根 `pom.xml` 的 `maven-compiler-plugin` 加 `<parameters>true</parameters>`。
- 注意：**其它卫星模块需重新构建**才生效；本次只重建了主数据模块。

### 2.3 实体表名与 schema.sql 不一致（6 处，已修）

`department / position / org_hierarchy / user_authentication / user_identity / user_profile`
六个 `@TableName` 少了 `agri_md_` 前缀（schema.sql 里的物理表都带该前缀）。
已全部改为带前缀，`user_authentication` 的 500 随之消失。

### 2.4 交付物不可独立部署（已修）

主数据 `pom.xml` 未把 `spring-boot-maven-plugin:repackage` 绑进构建，
`mvn package` 只产出普通 jar（无 `BOOT-INF`、无 `Main-Class`），
与 V2.0 第 3 章"九大子系统独立部署"直接冲突。已绑定 `repackage`。

### 2.5 网关：主数据 vhost 缺平台认证端点（已修，待 reload 验收）

`ops/gateway/conf/conf.d/30-mdm.conf` 原先把 `/api/` 全部转给 `mdm_backend`，
于是前端在 `localhost:8080` 上调 `/api/v1/sso/token`（换票）会打到主数据后端而不是认证中心，
**登录在第一步就断**。已补 `/api/v1/sso/` 与 `/api/v1/auth/` 两条 → `core_platform`；
存量 `/api/*`（非 `/api/v1/*`）仍走 `mdm_backend`。

## 3. 尚未修（按建议顺序）

> **2026-10-12 追加：3.1 与 3.2 已在本日第二轮修完，实测只读端点 42/42 全部 `code=200`。**
> 下面保留原始记述以便追溯；已修内容见第 6 节。

### 3.1 8 个 Mapper 语句"只声明不实现"（阻塞 8 个列表页）

`CustomerMapper / SupplierMapper / ProductMapper / RoleMapper / DictMapper / OrganizationMapper`
接口里声明了 `selectAdmin*List`（`OrganizationMapper` 另有 `selectOrgByTenantId`、
`selectOrgCertAuditList`），但对应 XML 里**一条都没有**——8 个 XML 现存语句全是
旧 `/api/*` 接口族的（`selectCustomerList`、`selectProductPage` …）。

这就是"admin 端是接口先行、SQL 未落地"的实证。

### 3.2 实体 ↔ 物理表字段漂移（系统性，29/30 张表）

以 `schema.sql` 为基准逐字段比对，结果：

- **29 个实体**至少有一个字段在物理表里没有对应列（合计 100+ 处）；
- 反向也存在：物理表有列、实体未映射（不报错，但字段取不到值）。
- `com.agri.common.entity.BaseEntity` 的 `remark` 字段**任何表都没有**——凡是继承
  BaseEntity 的实体，只要参与 `SELECT`/`INSERT` 就会踩到，`/user/list` 的 500 即由此而来。

**方向判断（有 PRD 为证）**：PRD 基线文档《主数据管理模块系统PRD.md》
第 1565 行给出 `contact_person`、第 549 行给出 `max_users` —— 这些是实体里有、DDL 里没有的字段。
即 **schema.sql 落后于 PRD 与实体契约**，修法应是**补 DDL（纯增量、不删列、不动存量数据）**，
而不是删实体字段。

### 3.3 页面数据兜底与演示数据

- 前端多个页面在接口失败时回落到**内置演示数字**（如总览页 128/3,542/567/8,934），
  必须改成"真数据或明确空态"。
- 物理库现状（实测 `information_schema`）：30 张表里**只有 3 张有数据**
  （`agri_md_user` 1、`agri_md_tenant` 1、`agri_md_role` 1），其余全 0 行。
  即使接口全通，列表页也会是空的——需要按 PRD 补演示数据。
- 另注：`DashboardServiceImpl` 的 `alerts`、`distributionStatus`（今日分发 1234）、
  `qualityDistribution` 等是**服务端硬编码**，不是查库结果，需按同一口径清理。

### 3.4 前端 API 契约（下一轮的入口）

`web/src/utils/api.js` 里相当一部分路径与后端**实际注册的映射不符**，例如：

| `GET /admin/masterdata/tenant` | `GET /admin/masterdata/tenant/list` |
| `GET /admin/masterdata/tenant/{id}` | `GET /admin/masterdata/tenant/detail/{id}` |

## 4. 验收方式（可复现）

```powershell
# 1) 取一枚平台令牌（SSO 授权码流程的两步）
$b = @{ clientId='mdm'; redirectUri='http://localhost:8080/sso/callback';
        username='admin'; password='Admin@123'; marketId=1 } | ConvertTo-Json
$code = ([regex]::Match((Invoke-WebRequest 'http://127.0.0.1:8090/api/v1/sso/login' -Method POST `
  -ContentType 'application/json' -Body $b -UseBasicParsing).Content,'code=([0-9a-f]+)')).Groups[1].Value
$tok = ((Invoke-WebRequest 'http://127.0.0.1:8090/api/v1/sso/token' -Method POST -ContentType 'application/json' `
  -Body (@{code=$code;clientId='mdm'}|ConvertTo-Json) -UseBasicParsing).Content | ConvertFrom-Json).data.accessToken

# 2) 打主数据接口
Invoke-WebRequest 'http://127.0.0.1:8083/admin/masterdata/dashboard' `
  -Headers @{Authorization="Bearer $tok"} -UseBasicParsing | Select-Object -ExpandProperty Content
```

### 6.1 补齐 7 个"只声明不实现"的 Mapper 语句 + 1 个整份缺失的 XML

| 文件 | 补充的语句 |
| :-- | :-- |
| `CustomerMapper.xml` | `selectAdminCustomerList`（+ 共用 `adminCustomerWhere`） |
| `SupplierMapper.xml` | `selectAdminSupplierList`（+ `adminSupplierWhere`） |
| `ProductMapper.xml` | `selectAdminProductList`（+ `adminProductWhere`） |
| `RoleMapper.xml` | `selectAdminRoleList`（+ `adminRoleWhere`） |
| `DictMapper.xml` | `selectAdminDictList`（+ `adminDictWhere`） |
| `OrganizationMapper.xml` | **整份文件此前不存在**，一次补齐 7 条：`selectOrgTree`、`selectOrgChildren`、`selectOrgByTenantId`、`selectAdminOrgList`、`countAdminOrgList`、`selectOrgCertAuditList`、`countOrgCertAuditList` |

共同的计数方法（`countAdmin*`）**与列表方法共用同一个 `<sql>` where 片段**：
各写一份 SQL 的话，只要有一处条件漏改，"总数"与"当页数据"就会按不同口径统计，且静默发生。

`roleSort` 必须显式 `AS` 起别名：VO 字段叫 `roleSort`，而列名 `sort_order` 在
`map-underscore-to-camel-case` 下只映射成 `sortOrder`，不写别名会得到一个恒为 null 的排序字段。

### 6.2 DDL 对齐（纯增量）

- 以**实体字段为契约**、以 MySQL 实际列集合为基准（不信文件解析，直接查 `information_schema`），
  比对出 29 张表共 **173 个实体字段在物理表中没有对应列**。
- 已写回 `backend/src/main/resources/schema.sql`（**+173 行、0 删除**），
  并生成一次性迁移脚本 `agri-master-data/db/20261012-add-entity-columns.sql` 供既有库使用。

  与现库逐列双向比对。结果：两侧差集**均为空**，30 张表 / 602 列完全一致；
  随后删除该验证库。

### 6.4 本轮新发现的另一个坑（环境）

在 Windows 控制台里用 `mysql.exe ... -e "source data.sql"` 导入含中文的 `data.sql` 会报
`Data too long for column 'real_name'`——**不是 schema 问题**，是客户端默认按 OEM 代码页
（cp936）解析 UTF-8 文件所致。加 `--default-character-set=utf8mb4` 即通过（实测 exit 0）。
应用自身走 JDBC，不受影响；这条只影响"手工导入"这一条路径。

### 6.5 种子数据乱码 —— 应用**自己**把中文写坏了（已修）

6.4 那条只解释了"手工导入"，但修完之后库里仍是乱码，于是继续往下挖，
发现真正的根因在应用侧：

```
spring.sql.init.encoding 的默认值是「平台默认编码」
```

中文 Windows 上平台默认是 **GBK**，而 `schema.sql` / `data.sql` 都是 **UTF-8** 文件。
于是 Spring 按 GBK 读 UTF-8 的中文 → 得到乱码字符串 → 再写进库。

实测证据（对 `agri_md_tenant.tenant_name` 取 `HEX()`）：

| 阶段 | 字节 | 含义 |
| :-- | :-- | :-- |
| 修复前 | `E7BBAF E88DA4 E7B2BA E7BB89 E786B8 E59F9B` | `绯荤粺绉熸埛` —— "系统租户"的 UTF-8 字节被当 GBK 解读 |
| 期望/修复后 | `E7B3BB E7BB9F E7A79F E688B7` | `系统租户` |

更糟的是 `超级管理员` 里的"员"字在 GBK 里对不上，被替换成 **U+FFFD**（`EFBFBD`）——
**不可逆的数据损坏**，不是显示问题。而且这个过程**不报错**，只在界面上表现为乱码。

修法：`application.yml` 的 `spring.sql.init` 下显式声明 `encoding: UTF-8`。
验证：清掉 3 行种子数据 → 重启 → 应用按自己的连接重新播种 → 三个字段的 `HEX()`
与 UTF-8 期望值**逐字节一致**；经网关取回的 JSON 里 `tenantName` 为 `系统租户`。

**影响面提示**：任何一个在中文 Windows 上首启的卫星模块都会踩这个坑；
`agri-platform` 下其它模块若也用了 `spring.sql.init` + 中文脚本，应一并补上这一行。

### 6.6 修复后的整体复测

经网关 `:8080` 用 SSO 换来的平台令牌，复测 42 个只读端点：**42/42 全部 `code=200`**。
返回体形态也逐项抽验过：分页接口返回 `{list,total,pageNum,pageSize,pages}`，
非分页接口返回裸对象；中文数据经"库 → JDBC → JSON → 网关"全程无乱码。
