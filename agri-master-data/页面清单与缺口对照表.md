## 四、用户端：口径不一致，需逐项核对

- PRD V3.0 第 5.3 节：**7 页**；
- 原型 v1：**15 项**（工作台、消息通知、我的档案、商品分类浏览、商品详情、商品申请创建、客户档案、供应商列表、数据字典查询、数据质量查看、分发订阅、AI智能助手、智能推荐、AI数据体检、智能血缘查询）；
- 现有 `.vue` 里 `views/userportal/` 恰有 **7 个文件**（UserHome / UserLogin / UserDataQuery / UserHelp / UserProfile / UserReport / UserSettings）。

三者数量对不上，**不猜**：可能是"PRD 7 页 = 原型 15 项里去掉 AI 类入口"，也可能是原型多做了。
核对方法：以原型 15 项为名，逐项在 PRD"第一部分"里找出处；对不上的按"原型独有"登记。

1. **栈对齐**：按 PRD §15.1 回归 Vue（Vue 3.4 + TS 5 + Vite 5 + Ant Design Vue 4 + Pinia 2），补齐入口/路由/状态与依赖；
2. **先让 46 个 `.vue` 能构建**（这是可验证的里程碑），React 遗留挪到 `legacy-react/` 保留可回退；

5. 再按运营端 43 页补详情页与审核类页面（现有实现缺得最多的那部分）。

### 7.4 顺带修复的后端缺口（有实测）

- 新增 `mapper/masterdata/ProductCategoryMapper.xml`、`ProductAttributeMapper.xml`：
  这两个 Mapper 的方法（`selectAll` / `selectByCategoryId` …）此前**只有声明没有 SQL**，
  品类树与属性接口必 500（与 2026-10-12 审计里 `*List` 族是同一类故障）。
  修复后实测：品类树返回 6 条（农产品/粮食作物/水果/蔬菜/农业生产资料/加工食品），属性列表 `[]`（表内暂无数据）。
- 后端重启口令：`agri-master-data/backend/application.yml` 里 datasource 密码是 `Agri@2024`，
  本机 MySQL root 实际是 `root`，直接 `java -jar` 会 `Access denied`；用

## 十九、按钮级 / API 级权限点落地（2026-11-02）

产品定义里「权限点」分两层：页面级（能不能进这一页）与按钮级 / API 级（能不能做这个动作）。
上一轮只做了前者。这一层的表其实一直在（`agri_md_permission` + `agri_md_role_permission`），
但**两张表 0 行、接口一调就 500**，原因是三层叠在一起：

1. 实体映射的不是真实列 —— `Permission` 把主键写成 `permission_id VARCHAR`（真实主键是 `id BIGINT`），
   其余字段全指向 2026-10-12 为"字段对齐"补的那串恒 NULL 列，所以谁都写不进去；
2. `PermissionServiceImpl` 调的三个自定义查询（`selectByParentId` / `selectByRoleId` /
   `selectAllPermissions`）在 mapper 里声明了却**没有对应 XML**，而 `mapper-locations` 确实加载了那批
   XML —— MyBatis 只在运行期抛 `Invalid bound statement (not found)`，编译期一句提示都没有；
3. 授权表真实列是 `perm_id`，实体写成 `permission_id`，即使前两条都修好，`role_permission` 也插不进一行。

所以这一节不是"补数据"，是把**目录 → 授权 → 拦截**这条链一次接通，并让它不可能与代码漂移。

### 19.1 库变更（`db/20261102-permission-points.sql`，可重复执行）

| 变更 | 为什么 |
| :-- | :-- |
| `agri_md_permission.module VARCHAR(64)` + `idx_md_perm_module` | 矩阵按控制器 `@Tag(name)` 分组，否则 199 条平铺没法看 |
| `agri_md_role_permission.idx_md_rp_perm (perm_id, del_flag)` | 收紧判定要反查"这个点有没有任何角色持有" |
| `perm_code` 放宽到 `VARCHAR(191)` | 编码装的是整条端点路径模板，实测最长 67 字符，原来的 64 会截不下 |

> `perm_code` 这一列不是"顺手加宽"：同步是一个事务，一条超长的编码会让**整批权限点回滚**，
> 矩阵上空无一物且不报错。先跑同步再补列就已经晚了，所以这条列宽变更属于本轮功能的一部分。

### 19.2 目录由真实端点同步，不手抄

`masterdata/service/PermissionPointCatalogService.java`：注入 `RequestMappingHandlerMapping`，
把当前应用**实际注册**的映射逐条落库。实测 `scanned=360 → created=199`（POST 69 / PUT 89 / DELETE 41，
分属 35 个模块）。

- `perm_code` = `METHOD + 空格 + 路径模板`，算法只在 `codeOf()`（:137）一处 —— 目录写入与拦截判定共用，
  两处各写一遍的话分隔符或大小写差一点，结果就是"目录里有这个点、鉴权永远查不到"；
- **只登记写方法**：权限点管的是按钮，按钮对应动作。读接口一旦被收紧，勾一个点就把别人的列表页整片锁死，
  那是事故不是授权；
- `perm_name` 取方法上的 `@Operation(summary)`，没有就退化成 `控制器#方法名`（如
  `CustomerController#save`）—— **不编中文名**，编出来的名字矩阵看着整齐却没人能验证；
- 作用域判定 `isScoped()`（:200）与拦截器同一处：`/admin/masterdata/**` + `/api/**`，
  但排除 `/api/auth/**`（登录端点必须永远可达）；
- 端点在代码里消失 → `retireMissing()`（:180）置 `del_flag=1`；端点又回来 → `revive()` 改回在册。

### 19.3 收紧语义：勾上即收紧，取消最后一个持有者即放开

`common/security/PermissionPointGuard.java:43` 起，判定顺序是：
非 HandlerMethod → 无登录态 → 平台超管（`permissions` 含 `*` 或角色 `SUPER_ADMIN`）→
不在 `isScoped` 范围 → 非写方法 → `isRestricted(code)` 为假 → 已持有该点 → 否则 403。

只有一条规则：**某个点一旦被任何角色持有，它就变成受管端点**；没有任何持有者时不拦。
这样不需要"启用/停用"开关列，语义也只有一条 —— 授权动作本身就是"我要开始管这个端点"的信号。
主体侧账号通过**用户名**桥到本地角色（`PermissionServiceImpl.localUserIdByUsername():178`，
账号存在但一个角色都没绑 = 没有本地身份），拦截器与「我的权限点」接口读同一套方法。

注册顺序在 `common/config/WebMvcConfig.java:46`：认证拦截器在前、权限点守卫在后，

### 19.9 前端按钮显隐（同日追加，`mdm@20261102-mdm-permission-button-r2`）

服务端会拦 ≠ 页面上看得见门。这一节把企业端的写按钮接到同一份判定上。

**口径只有一处**：`PermissionPointGuard.deniedFor(LoginUser)`（:80）返回"这个人会被拦"的编码集合，
拦截器逐请求问它，`/mine` 接口把它原样吐给前端。前端 `stores/points.ts` 只做一次成员判断，
**不复刻任何规则**（不判超管、不判 verb、不判作用域）—— 复刻一份就有两份口径，
迟早出现"按钮还在但一调就 403"或"按钮没了其实还能调"。
`isRestricted(code)` 随之删除，"已纳管"这条事实只剩 `restrictedCodes()` 一个入口
（代价是每个写请求多两次查询，换掉的是漂移；写请求是按钮点击量级）。

**主体侧必须有自己的读接口**：`GET /api/user/permission-points/mine`（`UserPermissionPointController`）。
运营端那条 `/admin/masterdata/permission/mine` 在 `operator-paths` 里，读它要 `masterdata:read`，
企业端账号本来就没有这个码 —— 让它去读运营端接口，按钮隐藏逻辑第一步就 403。

**接线的按钮**（`v-if="points.can('METHOD /路径模板')"`，编码就是目录里那条端点）：

| 页面 | 按钮 | 权限点 |
| :-- | :-- | :-- |
| 组织架构 `/user/org-tree` | 新增组织 / 行内编辑 | `POST /api/user/orgs`、`PUT /api/user/orgs/{id}` |
| 部门与岗位 `/user/dept` | 新增部门 / 新增岗位 | `POST /api/user/depts`、`POST /api/user/positions` |

| 企业工作台 | 新增客户 / 编辑 / 删除 / 保存联系信息 | `POST`、`PUT`、`DELETE /api/user/customers…`、`PUT /api/user/orgs/{id}` |

三条渲染纪律：① 隐藏不是静默消失，表头按钮消失时给一条「部分操作已隐藏」说明去哪儿开通，
行内按钮位置留「未授权该操作」，避免被误读成"这条数据不能改"；② 角色页把两种不可改分开显示 ——
`内置/共享` 是角色本身不能改，`未授权该操作` 是这个账号没被授权，混成一个文案就会误导人；
③ **权限点读不到时一律显示按钮**（`can()` 在 `denied` 为空时返回 true）——
把"读取失败"渲染成"没权限"会让人以为自己被回收了权限，那比多显示一个按钮更坏。

### 19.11 纠正 19.10：那"6 个路径 bug"里有 3 个是我的比对脚本造出来的

19.10 收尾时把 6 个没接上权限点的按钮归成"helper 路径写错"。逐条对回 `api.ts` 后，**其中 3 条不成立**：

| 结论 | 依据 |
| :-- | :-- |
| `updateProductAttribute` / `deleteProductAttribute` / `updateRegion` **路径没错** | `api.ts:451/453/485` 写的是 `/api/product/attribute/{id}`、`/api/master-data/address/regions/{regionId}`，后端确实注册了这两族（目录里能看到 `更新属性 / 删除属性 / AddressController#updateRegion`） |
| 它们没被接线是**我的比对脚本的 bug** | 那段一次性脚本对每条 helper 都无条件加 `/admin/masterdata` 前缀（`${BASE}` 的替换是空操作），于是所有非运营端前缀的 helper 都被拿去和 `/admin/masterdata/%` 的目录比，必然 0 命中 |
| 真正跨模块的只有 3 条 | `updateTradeProduct`、`updateTradeProductStatus`（`/api/trade/admin/product/manage/**`，交易域）、`updateMessageTemplate`（`/api/v1/admin/uc/message-templates/{id}`，core-platform） |

**补接线**：10 处，覆盖之前漏掉的 4 个页面 —— 属性模板（新增 / 编辑 / 删除属性）、行政区划（新增区划 ×2 处入口、
行内编辑）、编码规则（试算、启用·禁用）、标准与元数据（发布、停用）。接线判据也改了写法：
不再按"页面里出现过的 helper"匹配，而是**每条写 helper 反查目录、要求唯一命中，再检查该页是否真的绑了这个编码**，
所以漏一个就会明确报出来。现在的账目是：

- `api.ts` 里能对上主数据权限点的写调用 **65 处，已接线 65 处**（运营端 `v-point` + 企业端 `points.can`）；
- 剩下 **3 处不属于本模块**，主数据的权限点管不到它们，要收紧得去交易域 / 平台域各自的 RBAC。

**端到端补了一条独立分支**（`e2e-mdm-permission-ops-buttons.mjs` 第 7 节，25 项全绿）：
运营端页面调 `/api/**` 这一族时同样受管 —— 收紧 `POST /api/master-data/address/regions`、
`PUT /api/master-data/address/regions/{regionId}`、`POST|PUT /api/product/attribute…` 四个点后，

### 19.12 运营端「部分操作已隐藏」横幅（同日追加，`mdm@20261102-mdm-permission-notice-r6`）

企业端那条提示是逐页手写的 `NoticeBar`，运营端 31 个页面 / 73 处绑定不可能照抄一遍 ——
**页面自己维护一份"这页有哪些点"的清单一定会和按钮漂移**，漂移后的表现是
"按钮已经消失而横幅说没事"，比没有横幅更坏。所以这条横幅由指令自己登记：

- `v-point` 在每次判定时把编码登记进 store（引用计数 `hiddenCounts`），元素转可见或离开页面时释放；
- `components/ui/PointHiddenNotice.vue` 只读 `hiddenCodes`，挂在 `components/Layout.vue` 的
  `content-wrapper` 里（`AdminLayout` 是全部运营端路由的外壳），**运营端一处、页面零改动**；
- 计数按**编码**不按元素：区划页 3348 个行内「编辑」+ 1 个「新增区划」只算 2 项。

列编码而不是列中文名是有意的：目录里相当一部分名称是 `控制器#方法名` 的退化值，
而编码正是运营端「角色权限矩阵 · 接口权限点」里可勾选的那一项，操作员拿着它能直接对上要授的点。

判据跟着事实走，所以四种情形都验了（`e2e-mdm-permission-ops-buttons.mjs` 第 1/3/5/6/7 节，30 项全绿）：
未收紧时不出现（不是常驻一条"可能没权限"）；字典页只列这一页消失的两个编码、不把别页的点算进来；
换到区划页只列区划那两个；按钮回来后横幅随之消失（不留过期提示）；
超管 `admin` 什么都没被隐藏，因此也**不该看到这条横幅**。

回归：26+48+281+24+38 全绿，`ops/ci/verify.mjs` 63✓/1✗（仍是天地图 `tianditu.ts` 覆盖率）。

### 19.13 两端统一成一套显隐机制（同日追加，`mdm@20261102-mdm-permission-notice-r7`）

19.9 那批企业端提示是逐页手写的 `NoticeBar` + `v-if="points.can(...)"`，与 19.10 的运营端指令机制并存。
两套画法迟早分叉（改了一边的语义，另一边还在说旧话），这轮统一：

| 之前（企业端） | 现在 |
| :-- | :-- |
| 按钮 `v-if="points.can('CODE')"` | 按钮 `v-point="'CODE'"`（与运营端同一指令、同一登记） |
| 每页一条手写 `NoticeBar` + `HIDDEN_HINT` 常量 | 由 `UserLayout.vue` 挂同一个 `PointHiddenNotice`，内容来自指令登记 |
| 每页 `onMounted` 里 `points.load()` | 只在 `main.ts` 启动时读一次（`loaded` 有去重，页面重复调也是空操作，索性删掉） |
| 角色页 `editableRow = 角色可改 && 有点` | 拆成 `roleEditable`（角色本身）+ `v-point`（有没有点），占位文案各自独立 |

`HIDDEN_HINT` 常量随之删除（`PointHiddenNotice` 是唯一文案来源）。行内按钮的「未授权该操作」占位保留，
但判据从 `v-else` 改成显式 `v-if="!points.can('CODE')"` —— 指令是 `display:none`，元素还在，
`v-else` 分支根本不会渲染，照抄旧写法会得到一个空白格而不是说明。

> 同理，**点检脚本里"按钮消失"的断言必须改成数可见元素**。原来 `locator('button').count() === 0`
> 在 `v-if` 下成立，换成指令后元素仍在 DOM 里，这条断言会永远失败（或者更糟：改成永远成立）。
> 现在两端脚本共用 `visibleCount()`（`offsetParent !== null && style.display !== 'none'`）。

回归：企业端 27、运营端 31、权限点 48、页面回归 281、组织权限 24、巡检 38 全绿；
`ops/ci/verify.mjs` 63✓/1✗（仍是天地图 `tianditu.ts` 覆盖率）。

**至此权限点这条链的画法是单一的一套**：`deniedFor()` 算结论 → `v-point` 执行显隐并登记 →
`PointHiddenNotice` 在两个外壳各挂一次 → 行内留占位文案。页面不再维护任何"我有哪些点"的清单。

### 19.14 横幅的出口：一键申请授权 → 运营端处理 → 真的放开（同日追加，`mdm@20261102-mdm-permission-request-r10`）

19.12 的横幅只做到"说清哪些按钮被藏了，并告诉你去矩阵页开通"。**告诉你在哪儿开通 ≠ 你能开通**：
被拦的人没有运营端入口，而运营端也不会主动知道谁被拦了。这轮把这条路补成一条完整的链。

新表 `agri_md_permission_request`（`db/20261102-permission-request.sql`，已应用）：

| 列 | 口径 |
| :-- | :-- |
| `applicant` | **平台账号用户名**，不是主键。权限点本来就按"平台用户名 → 本地 `agri_md_user`"桥接，运营端令牌主键来自 core-platform、主体侧令牌来自本模块，存主键等于再造一套身份口径 |
| `applicant_name` | 令牌昵称快照。**本环境令牌没有 nickname → 这一列为空**，队列退回显示用户名（`applicantName \|\| applicant`），不编一个名字填上 |
| `perm_code` / `perm_name` | 提交时校验目录里真实在册（不存在直接 400），名称取快照以便点下线后申请单仍读得懂 |
| `page_path` / `reason` | 从哪个页面提的 + 为什么，处理人据此判断是哪个按钮 |
| `status` / `handler` / `handle_remark` / `handle_time` | `PENDING → APPROVED / REJECTED`；处理人取自令牌，不是写死字符串 |

**故意没有唯一键。**`agri_md_role_permission` 那一层已经踩过"全局逻辑删除 × 唯一键"：加了唯一键，
「驳回后重新申请」必然 `Duplicate entry`（旧行只是 `del_flag=1`，键还在）。所以判重放在服务层
（`PermissionRequestServiceImpl.submit`：同人同点已有 `PENDING` 就返回那条，不新建）。

> **建表来源补齐**（本轮顺带发现的同类缺口）：`spring.sql.init.schema-locations` 只指向 `classpath:schema.sql`，
> 而 2026-11-02 这几张新表**只写进了 `db/*.sql` 补丁**，`schema.sql` 里一条都没有 ——
> 新库启动后就是"接口 200 但表不存在"。现在 `schema.sql` 补齐 `agri_md_permission_rule` /
> `agri_md_role_mutex` / `agri_md_permission_anomaly` / `agri_md_permission_request` 四张表，
> 并把 `agri_md_permission.perm_code` 的宽度（64 → **191**，超宽会让整批同步在事务里静默回滚）、
> `module` 列、`idx_md_perm_module` / `idx_md_rp_perm` 两个索引，以及两张授权表的 `expire_time`
> （「过期权限」这条巡检口径唯一的数据源）一并写进建表语句。
> **种子数据（规则与互斥对）仍只在 `db/` 脚本里** —— 那是配置数据，不该由建表文件造。
> 已部署库不受影响：全部 `CREATE TABLE IF NOT EXISTS`；`schema.sql` 已在当前库上执行过一遍（exit=0），
> 并与 `information_schema` 逐列核对一致。

三处设计上的取舍，都是为了"这条链不是装饰"：

1. **同意就真授权** —— `handle()` 里调 `PermissionServiceImpl.grantCodeToUserRoles()` 写
   `agri_md_role_permission`，与鉴权拦截器读的是同一张表。不存在"同意了但还没放开"；
   申请人没有本地角色时抛 400 且**整笔事务回滚**，申请单保持 `PENDING` ——
   不能把"没办成"写成"已同意"，否则申请人以为开了其实没开。
2. **驳回必须写原因** —— 不写原因的驳回只会让申请人再提一遍，等于把队列变成噪音。
3. **申请入口自身不受权限点约束** —— `PermissionPointCatalogService.EXCLUDED_PREFIXES`
   加了 `/api/user/permission-points`（与 `/api/auth` 同一类理由：**逃生通道不能被这道门锁住**）。
   否则矩阵上勾一下这个点，所有被拦的人连申请都发不出去；目录里也不会出现一行"没人能勾却又必须永远可用"的点。

接口：主体侧 `POST /api/user/permission-points/requests`（申请人只认 `LoginUserHolder`，
请求体里传 `applicant` 改不了归属）；运营侧 `GET /admin/masterdata/permission/requests`、
`PUT /admin/masterdata/permission/requests/{id}/handle`（body `{approve, remark}`）。
`GET .../mine` 两端都补了 `pending` 数组，前端据此把已排队的点标成「已在排队」并禁止重复勾选。

> 顺手改掉一处会在页面上说谎的默认值：`listPermissionRequests` 原来在 `status` 为空时兜成 `PENDING`。
> 前端下拉里"全部"会被 `normalizeQuery` 丢掉空值 → 变成不传 → 后端兜成待处理，
> **页面显示"全部"、数据其实是"待处理"**。现在后端空值即不按状态筛，"默认看待处理"只留在前端那一处初始化。

页面：`PointHiddenNotice.vue` 加「申请授权」按钮 + 勾选弹窗（默认勾上全部未排队的项，逐条提交，
提交后 `points.load(true)` 刷新 pending）；`views/permission/RoleMatrix.vue` 加「授权申请」卡
（状态档下拉 + 同意一键 + 行内展开驳回原因）。19.12 横幅里那句"去矩阵页开通"随之被这颗按钮取代，
两个既有脚本的对应断言改成了"横幅上有可见的「申请授权」按钮"。矩阵页的格子仍然**不因观察者没权限而消失**。

端到端：`scripts/e2e-mdm-permission-request-loop.mjs` **51 项全绿**，两端真机点过（`outputs/mdm-permission-request-20261102/`）。
覆盖的分支与实测到的事实：

- 提交两条 → 落库 2 行（含 `page_path` 与理由）、`pending` 立刻回显、重开弹窗默认不勾且提交禁用；
- 服务端判重返回原单号；目录里没有的编码 400；请求体传 `applicant: 'admin'` 仍然记在 `farmer` 名下；
- 运营端队列按编码逐行看到这两条 → 驳回不写原因 400 且状态仍是 `PENDING` → 行内填原因确认后 `REJECTED|admin|原因`；
- 同意 → `agri_md_role_permission` 行数 1→2 且落在**他桥接的那个角色**上 → 申请人 `denied` 只剩被驳回那个 →
  企业端刷新「新增组织」回来（`visibleCount` 实测 1）、「编辑」仍然隐藏（0）、横幅从 2 项降到 1 项 →
  `POST /api/user/orgs` 200 落库、`PUT /api/user/orgs/{id}` 仍 403；
- 已驳回的点可以再申请（同点第二行 `PENDING`）；已处理完的单子重复处理 400；不存在的单号 404；
- `provider`（本模块无本地账号）能提单但同意被 400，`agri_md_role_permission` 零残留；
- 运营端非超管 `mdmops` 读得到队列，也走同一个申请入口（提一条、驳回一条，不留悬挂数据）；
- 清理：申请单、授权、测试角色、本地账号、本次建的组织全部归零（`request=0 holders=0/0/0`）。

一处实测纠正：`provider` 带 `X-Agri-Merchant: 2001` 调 `/api/user/permission-points/**` 会得到
`3002 当前账号不属于该经营主体`——申请与「我的权限点」只认令牌，**不带主体头**（脚本里已经按这个改）。
被拦的人恰恰是最不知道该报哪个主体的人，出口不能再要一次归属证明。

#### 本轮自己造出来又靠回归抓到的死按钮（记死这条）
