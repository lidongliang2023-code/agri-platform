# 用户与经营主体绑定方案（建议稿，未动代码）

状态：**方案待拍板**。本文只描述模型与迁移路径，没有修改任何代码或表结构。

## 一、为什么必须解决它

它同时卡住了两侧，而且方向相反：

| 现象 | 现状 | 后果 |
| :-- | :-- | :-- |
| 用户端"只看自己的" | 平台没有"用户 ↔ 经营主体"映射，算不出自己的范围 | 2026-10-13 已把两处"不传范围就返回全平台"的兜底改成**必须指定参与方**（越权面关闭）；用户端因此**查不到数据** —— 正确但不可用 |
| 按 id 取详情 | `GET /order/{id}`、`GET /demand/{id}` 等**不校验请求者有没有权看这一单** | 换个 id 就能看别人的单据；这类问题需要同一套身份口径一起收口 |

所以这不是"补个过滤条件"，而是**缺一层身份关系**。

## 二、现状盘点（实测，不是推测）

| 表 | 关键字段 | 能否定位到"某个人" |
| :-- | :-- | :-- |
| `agri_core.platform_user` | id, username, password, nickname, phone, status | 是（平台账号本体） |
| `agri_core.platform_merchant` | id, market_id, tenant_id, code, name, type, credit_code, contact_name, contact_phone, status | **否 —— 没有任何指向用户的字段** |
| `agri_md_user`（主数据） | id, user_code, username, tenant_id … | 是，但 **id 与平台 user id 不是同一套**（主数据 admin 是 3，平台 admin 是 2108130996492058625…） |
| 交易模块各表 | `buyer_id` / `seller_id` / `complainant_id` / `applicant_id` | 这些 id 目前来自演示数据里的"商户号"（2001-2006 / 3001-3004），**与任何一张用户表都对不上** |

结论：**今天没有任何一条数据能回答"这个登录用户是哪个买家/卖家"**。

## 三、建议的模型

在平台侧新增一张绑定表（放 `agri_core`，因为它管身份；放主数据侧也可以，但身份是平台职责）：

```sql
CREATE TABLE platform_user_merchant (
  id           BIGINT      NOT NULL AUTO_INCREMENT,
  user_id      BIGINT      NOT NULL COMMENT '平台用户ID（platform_user.id）',
  merchant_id  BIGINT      NOT NULL COMMENT '经营主体ID（platform_merchant.id）',
  role_in_merchant VARCHAR(32) NOT NULL COMMENT '主体内角色：owner 负责人 / buyer 采购 / seller 销售 / finance 财务',
  status       INT         NOT NULL DEFAULT 1 COMMENT '1生效 0停用',
  created_at   DATETIME    NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_user_merchant (user_id, merchant_id),
  KEY idx_merchant (merchant_id)
);
```

要点与理由：

1. **一个用户可以属于多个经营主体**（合作社的采购员同时在加工厂任职是常态），所以是"用户-主体"多对多，而不是给 `platform_user` 加一个 `merchant_id` 字段。加单字段那一步做完，很快就要推倒重来。
2. **主体内角色单独存**（`role_in_merchant`）：它决定"这个人在这家主体里是买方还是卖方"。同一个用户在不同主体里的角色可以不同 —— 这在撮合场景里很实际（既是卖家又是买家）。
3. `platform_merchant` 已有 `market_id` / `tenant_id`，多租户与多市场隔离沿用现有口径，不新增概念。
4. 绑定关系由运营端维护（谁来录、要不要审批，见第五节）。

## 四、迁移路径（建议分三步，每步都可独立验证）

**第 1 步：建表 + 录入口（不改任何现有行为）**
- 加 `platform_user_merchant` 表；运营端加一个"用户-主体绑定"页（列表 + 新增/停用）。
- 同时给交易模块的数据补一次**主体对齐**：把 `buyer_id`/`seller_id` 等现有 id 与 `platform_merchant.id` 对齐（演示数据现在是 2001-2006 这种自造号，先对照一遍再决定是就地改号还是建映射）。
- 这一步结束时：老逻辑照跑，只是多了一张可维护的绑定表。

**第 2 步：交易模块改为按绑定解析身份**
- 交易服务通过平台/主数据接口拿到"当前用户 → 主体 id 列表 + 主体内角色"，据此推出口径：
  · 订单：`buyer_id ∈ 我的主体` 或 `seller_id ∈ 我的主体`
  · 纠纷：`complainant_id ∈ 我的主体` 或 `respondent_id ∈ 我的主体`
  · 这样用户端那两个页面**从"查不到"变成"查得到自己的"**，而现在这套"必须指定参与方"的守卫可以保留（由服务端解析后自己填，而不是让前端传）。
- 同一批把**按 id 取详情**的接口补上权限校验（换 id 看别人单据的问题）。

**第 3 步：收口与清理**
- 前端不再自报身份（现在是把登录用户 id 当参与方传，属于过渡做法），改为完全由服务端从令牌 + 绑定表推导。
- 巡检一遍还有哪些接口是"不传范围就全量"的写法。

## 五、需要你拍板的三件事

1. **绑定粒度**：一个用户能否属于多家经营主体（本文建议"可以"）。若确定"一人一主体"，模型可以退化成 `platform_user` 上加一个字段，但以后要改回来代价较大。
2. **谁维护绑定**：运营端人工录入，还是注册/认证流程里自动生成？如果是后者，注册流程需要先有"选择/创建经营主体"这一步。
3. **演示数据怎么对齐**：把交易模块里的 `2001-2006 / 3001-3004` 就地改成 `platform_merchant.id`，还是保留原号、另建一张映射？前者干净（建议），但要动演示数据与已有测试。

## 六、不做什么

- **不**给用户端接口加"看起来过滤了、其实永远返回空"的条件：那是把越权面伪装成正常功能。
- **不**在交易模块里直连平台库取用户信息：跨域取数要走平台接口，否则以后平台换库、交易模块会先崩。
- **不**在没有绑定关系时按 `contact_phone`/`name` 之类的字段去"猜"关联：猜错就是把 A 的订单给了 B。
