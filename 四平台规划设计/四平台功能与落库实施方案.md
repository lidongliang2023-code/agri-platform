# 数据中台、技术平台、独立运营平台与统一管理控制台

基于现有农业产业互联网平台的功能与页面设计 · 2026-11-11

## 1. 本次设计范围与判断

将“独立管理模块”解释为 `agri-admin` 承载的**统一管理控制台**。四模块可独立部署和授权，但不各建一套认证、主档、业务审批或消息引擎。独立部署不代表数据与权限自治到可以重复建库。

本次产出为设计方案与交互原型，不新启服务、不执行DDL、不变更业务数据，不宣称已完成接口联调或真实数据库写入。原型均为演示记录，操作用于查看交互和流转设计，不发起生产业务请求。

### 1.1 核对到的真实现状

| 范围 | 已有实现及限制 | 对本设计的影响 |
|---|---|---|
| 四个目标模块 | agri-data-platform / agri-tech-platform / agri-operation / agri-admin 只有POM与小型构建产物，无应用源文件、页面及独立迁移 | 全部作为待建设模块，不把构建登记当成运行能力 |
| 统一身份与主体 | core-platform维护账号、平台权限和经营主体；主体即租户，禁止独立新建第二份租户主档 | 新平台统一SSO，主体与权限通过现有API获取 |
| 主数据 | 已有标准、字典、编码、元数据、质量、分发、组织等后台 | 数据中台只补分析元数据与分析质量执行，引用主数据标准，不再建主数据治理产品 |
| 主数据分发 | 已在主数据域补真实发送执行器、不可变快照、稳定幂等键、逐次回执；旧汇总任务缺载荷时拒绝重放 | 已完成源码修复及隔离验证；目标系统接收契约与当前部署发布仍待联调，数据中台不另建分发 |
| 事件基础 | core-infra有Outbox、转发、退避和死信机制 | 在可复用实现上封装跨进程契约，不默认其他独立服务已经接入 |
| 消息 | 核心域增加任务数据库行锁、批次原子事务、任务与用户消息唯一键；针对并发与失败回滚完成隔离验证 | 继续复用核心投递；新增V61迁移随发布生效，短信/邮件未接入回执，不得标为打通 |
| 工单 | IoT运维工单、综合服务工单、用户反馈均有各自对象与状态机 | 独立运营只建跨域协作单和任务引用，不替代领域工单 |
| 文件 | 核心有认证材料专用上传，IoT有固件存储 | 通用文件中心是增量能力；不直接放宽原有认证材料访问范围 |
| AI | 场景、提示词版本、模型渠道、路由及熔断策略已改为AI域数据库配置，配置历史同事务保存；旧文件仅首次导入 | 配置CAS、重启读回、加密存储及引用校验完成隔离验证，当前服务尚未发布新版；运行审计和熔断通知仍沿用原日志/文件机制 |
| 权限 | core平台权限、主数据域菜单和数据权限并存；部分旧鉴权路径仍在迁移 | 明确平台准入与领域授权；读取、导出与写入都校验，不能只隐藏菜单 |

## 2. 总体边界：每类事实只有一个权威写入者

| 模块 | 主责 | 可以保存 | 不建设/不拥有 |
|---|---|---|---|
| 数据中台 | 接入业务结果，生产分析数据、指标与数据服务 | 数据集契约、采集运行、分析层表、指标版本、分析质量结果、血缘、授权与服务订阅 | 主体/字典主档、订单交易库、设备注册、金融决策、资讯采集器、AI模型配置 |
| 技术平台 | 共享技术能力与运行治理 | 技术能力登记、运行投影、故障事件、重放申请、文件元数据、配置版本、交付记录 | 业务任务、业务工单状态机、IoT协议与OTA、AI路由、独立消息收件箱 |
| 独立运营平台 | 跨域运营协同与效果追踪 | 运营目标、协作单、步骤引用、SLA、客群定义、触达编排、效果归因引用 | 商品/订单/优惠券/佣金/退款账本、内容CMS、授信审批、服务派单 |
| 统一管理控制台 | 统一入口、跨域治理视图与责任协调 | 应用入口描述、导航编排、个人偏好、待办投影、治理协调单与审计索引 | 用户密码、平台角色主库、租户主档、主数据标准、第二套审批引擎 |

### 2.1 现有业务域归属矩阵

| 权威域 | 独占事实/动作 | 新平台使用方式 |
|---|---|---|
| core-platform / 用户中心 | 账号、认证、经营主体、身份申请、平台RBAC、站内消息 | 统一认证、按权限读取、深链原单、复用消息投递 |
| 主数据 | 组织、品类客商、字典编码、标准、主档分发、现有套餐配额 | 引用ID和标准版本；进入已有界面维护；复制到分析层仅为只读快照 |
| 生产 | 农场地块、农事计划作业、采收批次、库存、实物溯源 | 生产事实入仓，原始单据回源，质量问题退回生产修正 |
| 交易 | B2B供需撮合、合同、订单、支付退款、交易结算 | 读取履约事件；协作步骤引用交易单，不直接改订单表 |
| S2B2C | 零售订单、平台供货、商家货架、营销执行、佣金售后 | 跨域计划引用原活动；不恢复旧独立供应商PC/移动应用 |
| 金融 | 融资产品、授信评估、贷款审批、还款与质押风险 | 提供可追溯分析特征，最终决策与审批留金融域 |
| IoT | 设备网关、遥测、告警、自动化、控制回执、OTA、设备工单 | 引用聚合遥测与设备健康；技术平台不重复建设接入引擎 |
| 资讯 | 内容、行情采集、课程、推荐与资讯运营 | 接入已采集行情，不重写爬采任务与内容审核 |
| 综合服务 | 服务商、服务需求、服务工单、投诉与结算复核 | 引用服务单执行跨域协调；不另建派单引擎 |
| 政府监管 | 监管范围、执法检查、监管任务、整改闭环 | 仅在授权监管范围内提供指标；平台运营不审批行政执法单 |
| AI中台 | 场景、提示词、模型渠道、调用审计、故障转移 | 可选调用已发布场景；配置和调用详情进入AI原页面 |

### 2.2 导航与应用命名

四个应用逻辑前缀建议为 `/data-center/`、`/tech-center/`、`/operation-center/`、`/admin-console/`；仅为待登记路由，不是已部署访问地址，不在本设计预占端口。

应用描述优先扩展现有 `ops/modules/catalog.json` 的部署登记，补充应用ID、所有者、入口、健康探针、SSO client与权限点。统一管理库只保存运行时展示和导航编排，不再维护冲突的第二份部署清单。发布时由现有网关完成路由配置。

## 3. 数据中台：10个页面

角色：数据管理员、数据工程师、指标负责人、分析师、数据服务消费者。所有页面显示数据范围、统计时间、数据新鲜度与责任人。

| 页面 / 建议路由 | 核心内容及字段 | 主要操作与约束 | 责任及存储 |
|---|---|---|---|
| 数据总览 `/overview` | 任务健康、延迟、已发布指标、服务调用、质量问题 | 按领域/主体/日期过滤，异常钻取；空数据不显示虚构0增长 | 聚合运行记录与分析结果 |
| 数据源与接入 `/sources` | 来源域、数据集、API/事件方式、字段契约、负责人、授权范围 | 登记、连通性测试、提交接入；凭据仅引用技术平台secretRef | dp_source、dp_ingestion_contract |
| 同步任务 `/pipelines` | 契约版本、初始水位、增量游标、调度、目标表、重试 | 草稿→校验→发布；运行/暂停/补数；不得把测试连通当完整同步 | dp_pipeline、dp_pipeline_run |
| 数据资产目录 `/assets` | 数据集/字段、分层、责任域、标准引用、敏感等级、更新周期 | 检索、申请使用、查看口径；业务主档编辑深链主数据 | dp_dataset、dp_dataset_version |
| 指标中心 `/metrics` | 指标编码、公式、粒度、维度、过滤条件、版本、责任人 | 试算、对账、审批发布、废弃；已发布口径不可原地覆盖 | dp_metric、dp_metric_version |
| 分析质量 `/quality` | 源标准ID、完整性/唯一性/新鲜度、批次、影响范围 | 执行、隔离、分派回源；主档质量规则回主数据维护 | dp_quality_binding、dp_quality_result |
| 血缘与影响 `/lineage` | 来源→任务→数据集→指标→服务，字段级映射 | 查看变更影响；有下游依赖时阻止直接删除 | dp_lineage_edge |
| 专题分析 `/analysis` | 产销履约、产业运行、客户增长、质量风险专题 | 维度下钻、明细回源、导出申请；B2B和零售指标分开呈现 | 分析ADS与报表定义 |
| 数据服务 `/services` | 服务编码、指标版本、输出Schema、范围、配额、SLA | 沙箱验证→发布→订阅；预览脱敏；停用需通知订阅者 | dp_data_service、dp_service_subscription |
| 授权与对账 `/access-reconcile` | 使用方、用途、有效期、字段策略、水位、源/目标数量金额 | 授权审批、到期回收、差异复核；导出可撤销下载 | dp_access_grant、dp_reconcile_run |

指标必须明确：计量单位、时区、发生时间与入仓时间、订单状态、取消/退款口径、去重键、迟到窗口与回溯策略。交易额不可直接把大宗B2B与零售重复累加；跨域同一实物用sourceDomain/sourceObjectId及关系映射识别，不按商品名称合并。

建议首批数据集：生产采收事实、B2B订单履约事实、零售订单事实、IoT小时聚合、服务履约事实、行情日序列、主数据主体维度。敏感授信和监管资料不默认进入通用客群与营销数据集。

分层采用ODS原始只读、DWD明细、DWS聚合、ADS应用。平台初期可按现有MySQL能力分库存储小规模分析，设置时间分区、索引、保留期和容量阈值；遥测明细规模大时保留在IoT时序存储，只接聚合。CDC、专用数仓/时序产品需容量与运维评估后选择，不假定已经安装。

## 4. 技术平台：10个页面

角色：平台技术管理员、SRE、集成人员、安全管理员。基础组件写操作受动作权限和范围约束。

| 页面 / 建议路由 | 核心内容及字段 | 主要操作与约束 | 责任及存储 |
|---|---|---|---|
| 运行总览 `/overview` | 应用健康、事件积压、投递失败、容量、部署版本 | 从已有探针聚合，明确采样时间；未知与离线分开 | tp_health_sample、运行投影 |
| 应用与接口契约 `/applications` | 应用登记引用、负责人、版本、API Schema、依赖 | 导入部署清单、契约比对、兼容检查；非新账号库 | tp_api_contract、能力登记 |
| 事件与重放 `/events` | eventId、来源、积压、消费组、重试、死信 | 查轨迹、申请重放；复用Outbox，跨服务接入须补适配 | tp_replay_request、投递索引 |
| 通知通道 `/notifications` | 通道能力、模板引用、投递健康、回执与限流 | 复用核心消息任务；模板内容回核心维护；短信邮件标未接入 | tp_channel_binding、技术回执 |
| 任务运行治理 `/jobs` | 原任务ID、所属执行器、调度、互斥、超时、运行记录 | 运行记录汇聚、补偿请求；农事任务不是技术作业 | tp_job_binding、tp_job_run |
| 文件与导出 `/files` | fileId、所属域、用途、存储key、哈希、可见范围、到期 | 上传、授权下载、隔离清理；不接管原认证材料读权限 | tp_file_object、tp_export_job |
| 配置与密钥引用 `/config` | 应用、环境、配置版本、变更单、secretRef | 校验→审批→发布→确认→回滚；页面不展示密钥值 | tp_config_version、tp_config_release |
| 可观测与故障 `/incidents` | traceId、指标日志链接、告警归并、负责人、恢复时间 | 认领、关联发布、发协作请求；不替代IoT告警处置 | tp_incident、tp_incident_event |
| 发布与回滚 `/releases` | 制品哈希、兼容性、迁移版本、灰度计划、回滚点 | 复用现有网关发布机制；破坏性迁移禁止盲目回滚 | tp_release、tp_release_step |
| 集成与配额 `/integrations` | 技术调用方、证书引用、回调白名单、频率、容量 | 技术限流和轮换；用户授权仍回核心，商业套餐回主数据 | tp_integration_binding、tp_runtime_quota |

技术平台不默认新造调度器、消息队列、搜索或对象存储。先登记已有能力和协议，再以适配器治理；没有执行引擎的页面显示未接入，不产生“已执行”结果。

通用文件中心先支持新平台的导出与附件。原认证材料、IoT固件迁移需各域独立评估，未迁移前继续使用原存储和鉴权。

## 5. 独立运营平台：9个页面

角色：运营负责人、跨域协调员、客户成功、活动运营、效果分析师。运营平台有编排权，不因此获得各域审核权。

| 页面 / 建议路由 | 核心内容及字段 | 主要操作与约束 | 责任及存储 |
|---|---|---|---|
| 运营驾驶舱 `/overview` | 目标达成、跨域阻塞、SLA、触达转化、业务域贡献 | 指标来自数据服务，显示版本和新鲜度 | op_goal及指标订阅引用 |
| 跨域协作单 `/cases` | caseId、协作类型、主体引用、关联单、责任域、步骤、SLA | 创建、分派、催办、取消；步骤执行返回原域，回执后完成 | op_case、op_case_step、op_case_event |
| 主体服务旅程 `/journeys` | 入驻→认证→能力→商品→交易→售后里程碑 | 查看阻塞、发协作；主体/认证状态只读投影 | op_journey_projection |
| 客群与人群包 `/audiences` | 数据集授权、筛选版本、人数、用途、有效期 | 估算、生成快照、送审；禁用未授权金融/监管数据 | op_audience、op_audience_snapshot |
| 跨域活动计划 `/campaigns` | 目标、预算、参与域、渠道、原域活动ID、时间窗 | 创建计划、绑定已有活动、停止后续步骤；不生成优惠券账本 | op_campaign、op_campaign_binding |
| 触达编排 `/touchpoints` | 客群快照、核心模板ID、节奏、退订、投递任务引用 | 创建投递请求，幂等提交到核心消息；真实送达看回执 | op_touch_plan、op_touch_attempt |
| 服务SLA `/sla` | 协作时限、服务等级、升级规则、逾期对象 | 预警与升级；不能改变原域工单处理状态 | op_sla_policy、op_sla_breach |
| 运营实验与归因 `/experiments` | 实验分组、触达ID、转化事件、窗口、指标版本 | 分组、运行、归因分析；按曝光/转化ID去重 | op_experiment、op_attribution |
| 复盘与运营报告 `/reviews` | 计划、结果、成本、差异、改进责任人与截止日 | 引用指标快照、发起改进协作、导出 | op_review、op_review_action |

客群可有运营偏好与旅程标签，但主体法律属性、实名、会员身份和资质不归本平台。触达遵循用途授权、渠道可达性、退订和静默规则；落库记录“请求已受理/已投递/送达/失败”四种不同事实，不能把受理当成功。

## 6. 统一管理控制台：9个页面

角色：平台管理员、治理协调员、审计员、子系统负责人。管理台本身不提供额外越权入口。

| 页面 / 建议路由 | 核心内容及字段 | 主要操作与约束 | 责任及存储 |
|---|---|---|---|
| 管理工作台 `/overview` | 本人待办、服务状态、治理风险、常用应用 | 按真实权限聚合；错误明确显示来源不可用 | ac_todo_projection与个人偏好 |
| 应用入口与导航 `/applications` | 应用ID、责任人、部署登记、SSO client、准入能力 | 导航编排、开通申请；入口清单来自现有模块登记 | ac_navigation、ac_app_presentation |
| 统一待办 `/todos` | 来源域、单据ID、类型、优先级、状态版本、办理链接 | 去重展示、认领协调、回原单办理；不复制审批决定 | ac_todo_projection |
| 主体与权限治理 `/governance` | 主体状态、角色范围、异常授权、配额链接 | 主体/用户/RBAC/套餐跳原系统；协调单可落本库 | ac_governance_case |
| 标准与数据治理 `/data-governance` | 主数据标准、分析质量、消费影响、责任域 | 分域查看并深链；不再新增字典/编码维护页 | 来源API，只存索引 |
| 服务目录与负责人 `/ownership` | 业务能力、API责任人、数据所有者、SLA | 维护职责映射和联络，技术契约回技术平台 | ac_ownership_binding |
| 变更与治理协调 `/changes` | 变更主题、影响域、原域审批ID、发布单ID、回执 | 收集意见与就绪检查；不替代原域审批/发布状态 | ac_change_coordination、ac_change_link |
| 全域审计检索 `/audit` | 操作者、动作、域、对象、traceId、原记录定位 | 授权搜索、回源核验、导出申请；索引失败可补偿 | ac_audit_index |
| 个性工作台 `/preferences` | 常用入口、布局、订阅、个人范围偏好 | 仅保存本人偏好；平台安全策略回核心维护 | ac_user_preference |

重复菜单治理：原用户中心、主数据、AI后台不下线也不复制。管理台同名入口采用“责任域 + 能力名”，点击进入原系统，后续可统一外壳但不改变原API与事实归属。

## 7. 页面与交互统一规范

- 一级导航左侧对齐；二级导航不放图标、数量或连接线。四应用使用同一外壳、面包屑、搜索和详情抽屉。
- 采用现有管理列表样式规范：浅绿色背景、绿色主色、紧凑同行筛选、连续记录用列表/表格、状态同时有文字，非每条记录一张卡片。
- 总览可使用少量指标卡；列表列为名称/编码、责任域、状态、更新时间、责任人、操作。宽屏紧凑显示，小屏允许表格横向滚动。
- 详情统一“概览 / 流程 / 数据契约 / 变更审计”；明确对象权威域、读写责任、版本、失败处理与关联原单。
- 表单给出必填、唯一编码、枚举、长度、时间窗与跨字段验证；提交前展示变更差异。冲突返回最新版本并允许重载，不静默覆盖。
- 任何写操作需等待服务端事务结果；异步动作返回任务ID，显示“已受理”并轮询回执，不提前显示已完成。
- 页面必须实现加载、空态、无权限、来源不可用、部分结果、过期数据、写冲突与执行失败状态。部分聚合成功不能显示全平台正常。
- 深链仅使用部署登记的应用和路由白名单，携带objectId与traceId，不在URL传递Token、敏感字段或任意回跳地址。

## 8. 数据库与一致性设计

### 8.1 库与数据所有权

建议分别建立 `agri_data_platform`、`agri_tech_platform`、`agri_operation`、`agri_admin`，仅在开发阶段执行审批后的迁移。这是待建库名，不是已存在数据库。

每服务数据库账户只写自己的schema；查询外域采用API、事件或经授权只读抽取，禁止跨库UPDATE与共享Mapper。各域保留原有业务审计；新平台持久化自身操作事实和跨域调用回执。

主体范围不得一刀切：租户业务记录使用真实tenantId；平台全局配置使用scopeType=PLATFORM且无业务主体；双边交易按sourceBuyerId/sourceSellerId及原域可见性处理；监管数据按授权区域/机构处理。禁止用tenantId=0混合表达未知主体与平台全局。

### 8.2 建议实体与关键约束

除前述页面实体外，以下是首批最小闭环的关键落表要求，表名均为建议设计：

| 表/对象 | 关键字段 | 唯一性与一致性 |

### 8.3 跨域写入与事件契约

```json
{
  "eventId": "<全局唯一字符串>",
  "eventType": "production.harvest.completed",
  "schemaVersion": 1,
  "sourceDomain": "production",
  "aggregateType": "harvest_batch",
  "aggregateId": "<源批次ID字符串>",
  "aggregateVersion": 7,
  "scope": { "type": "SUBJECT", "subjectId": "<核心经营主体ID>" },
  "occurredAt": "<带时区时间>",
  "traceId": "<链路ID>",
  "payload": { "batchId": "<批次ID>", "quantity": "100.00", "unit": "kg" }
}
```

以上为建议事件契约，不表示现有生产服务已发送该事件。发布前应做Schema注册、兼容校验、敏感字段检查和源域授权。

- 同域：验证身份与数据范围→校验版本/状态→本地事务写业务记录与Outbox→提交后返回结果。唯一冲突返回可识别业务码。
- 跨域：使用Idempotency-Key创建请求记录→目标域按自己的授权与状态机执行→回执包含sourceObjectId、sourceVersion、resultStatus→发起域更新协作状态。
- 网络超时表示“结果待核验”，不等于失败；按幂等键查询原结果，禁止用户重复点按钮造成重复单据。
- 事件按至少一次投递设计；消费者事务内写inbox与本地投影，重复事件不重复扣减或触达。乱序以源版本控制；缺版本/断层进入补偿与回源核验。
- 死信重放需保留原因、范围、审批和结果；业务幂等仍使用原eventId。不可宣称分布式恰好一次投递。
- 跨域撤销采用可补偿步骤；已发货、已送达消息、金融审批等不可简单回滚。编排取消只停止未执行步骤并展示不可撤销结果。
- 重要授权/配置发布的本域变更与本域审计同事务提交；向全域审计索引发送失败可重试，不影响原审计完整性。不得沿用“日志失败仅告警”来满足关键变更审计要求。

### 8.4 分析同步与对账

首次快照以源域可重复读取的快照标记/时间窗获取，记录初始水位后衔接增量。API分页需稳定排序与游标；每页数据、检查点和目标批次状态事务化，失败仅重试未提交部分。没有可靠事件或CDC时采用更新版本/时间戳增量加周期全量对账，明确删除标记与时间精度限制。

分析质量失败进入隔离区或阻止发布；未通过质量和金额/数量对账的数据集不得作为正式数据服务。迟到与退款事件按口径回溯历史分区，重算记录指标版本及修订时间。任何“补数完成”都要有行数、校验和/金额、差异与对账结果。

## 9. 五条跨平台流程

### A. 采收数据到产销分析

生产提交采收→生产事务落批次及事件→接入服务校验并入ODS→分析任务生成DWD/ADS→质量与源批次数量对账→发布指标版本→运营驾驶舱订阅。失败分别留在源Outbox、采集运行或分析隔离区；数据中台不修改生产采收量。

### B. 新主体服务开通

用户中心注册/认证→core形成经营主体与授权→管理台待办引用→运营平台建跨域开通协作单→各业务域回原页面开通并落业务配置→回执更新步骤→管理台展示结果。主体主档只建一次；跨域部分失败不会把核心主体删掉回滚。

### C. 跨域营销与触达

数据中台授权数据集→运营平台定义客群并生成版本快照→建立跨域活动计划→绑定S2B2C已有营销活动/资讯已有内容→复用核心消息模板与任务→技术平台跟踪投递回执→交易/商城转化事件进入数据中台→按归因窗口复盘。优惠券发放和核销始终由商城落库。

### D. 故障影响业务与恢复

技术平台发现服务故障→聚合技术事件→运营平台记录受影响协作与SLA→管理台通知责任人→技术平台关联修复发布与回滚→事件恢复后对积压请求幂等补偿→源域回执确认→关闭故障和协作单。恢复探针UP不自动表示业务补偿已完成。

### E. 数据质量问题回源

分析任务发现异常→数据中台保存质量结果与影响→运营协调单分派给源域责任人→源系统修正原记录并发新版本事件→数据中台重算并对账→验证通过关闭。若源为主数据标准/主档问题，进入现有主数据质量流程；不在新平台修改同名主档。

## 10. 接口设计与权限

新增接口均为建议契约，未部署。前缀分别 `/api/v1/data-platform`、`/api/v1/tech-platform`、`/api/v1/operations`、`/api/v1/admin-console`。

| 契约组 | 示例动作 | 成功的判断依据 |
|---|---|---|
| 数据 | POST /pipelines/{id}/runs；POST /metrics/{id}/versions/{v}/publish；GET /runs/{id} | 运行创建返回202与runId；发布必须质量与对账通过 |
| 技术 | POST /events/{id}/replay-requests；POST /files；POST /config-releases | 请求受理与最终完成分开；文件返回已持久化fileId |
| 运营 | POST /cases；POST /cases/{id}/steps/{key}/dispatch；POST /touch-plans/{id}/submit | case本地事务完成；外域执行以回执为准 |
| 管理 | GET /todos；GET /audit；PUT /preferences；POST /change-coordinations | 查询带scope与来源新鲜度；偏好只能写本人 |

分页统一返回items/total/page/size；单条返回id/version/status/updatedAt；异步返回requestId/taskId/statusUrl。错误分为INVALID_ARGUMENT、FORBIDDEN_SCOPE、VERSION_CONFLICT、SOURCE_UNAVAILABLE、TARGET_RESULT_PENDING，附traceId；不能把HTTP 200直接判为业务成功。

权限点建议data:*、tech:*、operations:*、console:*，只作为命名空间建议，须在现有core权限体系登记。原域操作仍要求原权限；console:todos:read不等于业务审核权限。技术服务间使用可轮换的应用身份、最小scope和超时，不能把平台超级管理员Token作为固定集成凭据。

监管按机构与区域，经营主体按成员和数据范围，分析师按字段用途与有效期控制。聚合页先过滤可访问域，再请求；导出任务创建与下载时均复核权限，过期授权令已有下载地址失效。

## 11. 分期实施与验收

### 第0期：边界及接入基线（建议3–5工作日）

确认每域负责人、源API与Schema；冻结主档写入矩阵；登记四应用与权限；评估平台/主数据旧鉴权并存；验证核心消息多实例领取；确认Outbox独立服务接入方式。修复主数据分发执行缺口与关键审计可靠性。时间为待评估人日规模，不是交付承诺。

### 第1期：最小真实闭环（建议2–3周，需前后端/数据协作）

首批只做：管理台统一入口和待办；技术平台应用健康、事件运行及重放申请；数据中台生产采收入仓、指标和对账；运营平台一个“主体开通”协作模板。必须包含迁移、权限、回执和失败重试，不先铺满全部菜单。

### 第2期：数据服务与跨域运营（建议3–4周）

接交易/商城/服务等数据；指标发布、客群授权、触达编排与归因；技术通用文件和导出；统一审计索引。短信/邮件仅在接入真实通道、拿到回执并验证后开放。

### 第3期：规模化与治理（容量评估后排期）

分区、归档、专用数仓适配、多实例压力、灾备恢复与发布演练。AI配置迁库由AI域独立推进，保留原API，版本校验和审计不能丢失。

### 必须执行的验收用例

| 测试 | 验收结果 |
|---|---|
| 重复提交同一协作/投递请求 | 只产生一条目标业务动作或一次投递 |
| 同一事件消费两次、乱序消费 | 无重复统计，旧版本不覆盖新版本 |
| 目标已提交但响应丢失 | 发起方按幂等键查到原结果，状态可恢复 |
| 采集写入后进程崩溃 | 水位与数据一致，可从上次已提交检查点恢复 |
| 数据晚到、退款、删除 | 对应历史口径修订并显示修订时间，金额对账一致 |
| 源域离线、部分聚合失败 | 页面明确降级，不用空数组或0伪装正常 |
| 跨主体、跨监管区域访问 | 列表、详情、导出、回源都被后端拒绝 |
| 两人同时修改同一版本 | 一人成功，另一人得到版本冲突，无静默覆盖 |
| 权限撤销后下载旧导出 | 下载被拒绝，审计有记录 |
| 外域审批驳回或业务撤销 | 协作步骤反映原结果，不自动显示全部完成 |
| 文件写入成功而元数据失败 | 文件隔离且可清理，不生成可访问孤儿文件 |
| 服务重启/扩容到两实例 | 无双重领取、无重复触达，配置与任务持久可恢复 |
| 主数据分发重试 | 接收方真实收到数据并落库；不能仅检查发送状态变了 |
| AI后台与统一管理同时访问 | 共用AI原配置，未产生第二份场景/模型主库 |

上线判定同时看：源库记录、目标库记录、唯一约束、回执、事件轨迹、审计与页面状态。只有页面展示或接口返回成功不足以验收“正常落库”。

- 主数据：新增创建真实分发任务接口、不可变载荷表、逐次尝试表、受限目标地址、30秒发送超时、120秒任务认领及原幂等键重试；成功必须有业务回执和一致数量。历史任务缺快照时保留失败状态，不能用演示数字伪造数据。暂停仅适用于未发出的排队请求。接收方须按幂等键去重，事务落库后返回 success、idempotencyKey、acceptedCount、receiptId；当前不假设各业务域已经实现该接收契约。
