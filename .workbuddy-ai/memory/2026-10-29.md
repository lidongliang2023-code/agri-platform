## 消息推送异步化（去掉 2000 人上限）

### 改造前的问题
请求里同步循环插站内信，还有 2000 人硬上限：
- 再多就超时；超时**不会回滚已插入的站内信** → 用户收到一半、运营看到 500；
- 上限本身是拍脑袋的数字，真实人群规模一上来就废。

### 现在的结构（两段式）
```
POST /message-pushes  → 建任务（status=queued）→ 立刻返回 taskId
MessagePushWorker     → 每 3 秒：
  1) queued → 解析人群 → 落 platform_uc_push_target（名单）→ sending
  2) sending → 取一批（默认 500）→ 插 platform_message → 删这批名单 → 累加 reach_count
  3) 名单空了 → sent
```
- **名单表而不是游标**：人群口径是跨表条件（已实名/企业成员/30 天未登录），
  用游标每批重算既慢，又会让中途状态变化的用户反复进出。名单固定下来后，
  投递只是"读一批、发一批、删一批"，进程重启也能接着发。
- 前端：选完人群立刻查 `GET /message-pushes/audience-count` 显示预估触达；
  提交后任务表每 2 秒轮询，`queued → sending → sent` 与 `触达/目标` 实时往上走。

### 踩的坑
1. **`@Transactional` 自调用失效**：`deliverBatch` 在 service 内部被自己调用，
   绕过 Spring 代理，事务注解等于没写 —— 那样"插了站内信但没删名单"的中间态无法回滚，
   重试会重复发送。改成由外部 Bean `MessagePushWorker` 调用。
2. **`deleteBatchIds` 是逻辑删除**：实体继承 BaseEntity，`deleted` 带 `@TableLogic`，
   那个方法执行的是 `UPDATE ... SET deleted=1`，名单行永远留在表里。
   每次群发几万行 → 表无限膨胀，正好违背"投完就清"的初衷。
   改成 Mapper 里的物理删除 `DELETE ... WHERE task_id=? AND id<=?`（按 id 上界，语句长度与批次无关）。
   **这个 bug 是实测发现的**：第一次跑完 status=sent 触达 29/29，但 `platform_uc_push_target` 还留着 29 行。
3. **批大小做成可配置**（`agri.uc.push.batch-size`，默认 500）：否则线上永远"一批就发完"，
   多批分支等于没被测过。用小批次（10）实测过 29 人跑 3 批。

### 验证
- 预估触达：all=29 / realname=5 / enterprise=6 / inactive=0
- 入队立即返回 `{taskId, status: queued}`
- 8 秒后：`status=sent 触达=29/29`，`platform_message` 23→52（+29），名单表 0 行
- 多批：`batch-size=10` → t+1s `sending 10/29` → 最终 `29/29`，无重复无遗漏
- 用户端能看到：`platform_message` 里 `read_flag=0` 的站内信，标题内容正确
- E2E 重跑：22 页全部渲染，0 console error
- 发布 `user-center-ops@20261029-uc-ops-r9`

### 仍存在的边界
- **单实例假设**：多实例同时跑 worker 可能重复投递同一批（没有分布式锁）。
  当前是模块化单体单实例部署；要多实例需加任务级 `SELECT ... FOR UPDATE` 或 Redis 锁。
- 微信/短信/APP 渠道仍未接（需要通道凭据），只记在任务的 channels 字段里。

## 用户详情页补「账号处置」：会话 / 强制下线 / 重置密码

### 为什么做这个
之前运营看到可疑账号，只能跳到「账号冻结」页手输 19 位雪花 ID，中间没有任何
"这个账号现在登在哪、能不能踢下线"的能力。处置动作是用户中心运营端的核心日常，缺它等于半个后台。

### 复用而不是重造
| 能力 | 复用的既有实现 |
|---|---|
| 会话列表 | `SsoSessionService.listSessions(userId, currentSid)` —— 与用户端「登录设备」同一份 |
| 强制下线 | `SsoSessionService.revokeAllForUser` + `AuthService.revokeAllSessions` |
| 重置密码 | `BCryptPasswordEncoder` + 上面两个吊销方法 |

**两件事必须都做**：只吊销访问令牌 → 旧 SSO Cookie 还能换一枚新的；
只清 SSO 会话 → 手里已发出的访问令牌仍有效到过期。

### 新增接口（`UserCenterActionController`）
- `GET  /admin/uc/users/{id}/sessions` 该账号活跃会话（设备/IP/登录时间）
- `POST /admin/uc/users/{id}/force-logout` 强制下线
- `POST /admin/uc/users/{id}/reset-password` 重置密码，返回一次性临时密码

单独一个控制器，不和只读报表、全局策略混在一起 —— 这三个接口都在动别人的账号。

### 设计取舍
- **临时密码只返回一次、不落库、不进审计详情**：审计只记"重置了谁的密码"。
- 临时密码 16 位、四类字符各至少一个、剔除 `0/O/1/l/I` 易混字符：
  这样无论运营把密码策略调成哪一档，临时密码都符合规则。
- 重置密码同时吊销全部会话 + 给用户发站内信（**站内信里不写密码**，站内信可能被他人看到）。
- **已知缺口**：平台没有「首次登录强制改密」标记位，临时密码在用户自行修改前一直有效。
  页面明确写了这一点，并提示必须走安全渠道转告。

### 踩的坑
1. **`UserEntity` 没有 `marketId`**：`platform_user` 是全局表（在 `agri.market.ignore-tables` 里），
   实体也没有该字段。写 `user.getMarketId()` 直接编译不过；站内信的市场维度交给
   `MyMetaObjectHandler` 自动填。
2. **会话时间是 epoch 毫秒字符串**：Redis 里只存了 `loginAt` 毫秒数，加上 Long→String 序列化，
   前端拿到的是 `"1793230971215"`，直接丢给 `formatTime` 会原样显示一串数字。
   新增 `formatMillis()` 专门处理。
3. **`current` 字段在运营端永远为 false**：`listSessions(userId, null)` 传 null 表示"没有本机"，
   所以"本机"标签永远不出现 —— 直接删掉那段渲染，不留死代码。

## 冻结申诉闭环（`appeal_status` 从"有字段没入口"变成真功能）

### 核心难点：被冻结的人登不进来
账号冻结 = `platform_user.status=0` → `AuthService.authenticate` 直接抛 `USER_DISABLED`。
所以申诉**必须免登录**，否则等于"被冻结的人永远没机会申诉"，这个入口不如不做。

### 三层改动
**1. 登录页（agri-sso/frontend）**
- 「账号 + 密码」行加了「账号被冻结？提交申诉」入口，走 `appealOpen` 视图（复用「忘记密码」的同一套切换方式，不新造弹层）
- 表单：注册手机号 + 申诉理由（textarea），提交后展示结果态
- 登录失败文案改成可操作：「账号已被停用或冻结，如认为有误，请在登录页点击「账号被冻结？提交申诉」申请复核」

**2. 公开接口（`FreezeAppealController`，`POST /api/v1/sso/freeze-appeal`）**
- **必须加进 `JwtAuthFilter` 白名单**（`/api/v1/sso/**` 不是全放行，逐个列出来的）——
  漏了就是 401，我第一次跑就踩了
- 校验：手机号格式 → 理由 5-500 字 → 用户存在 → 有 active 冻结记录 → 不能重复申诉（409）
- 不加短信验证码：通道未配置时会把整条路堵死，而申诉不涉及敏感数据
- 返回冻结类型与时间（让用户知道在对什么提异议），不返回运营内部完整原因

**3. 运营端（`UserCenterPolicyController` + 冻结页）**
- 列表加 `appealStatus` 筛选（默认「申诉中」），返回申诉理由/时间/处理意见
- `POST /freeze-records/{id}/appeal` `{approved, remark}`：受理=解封，驳回=保持冻结
- **驳回必须填理由**（400 拦），否则用户不知道原因，会立刻变成二次申诉
- 解封逻辑抽成 `applyUnfreeze`，「直接解封」与「申诉受理」共用，避免只改一处

### 状态机（实测全部通过）
```
冻结            → frozen / none      user.status=0
提交申诉        → appealing          重复提交 409
驳回(无理由)    → 400「驳回申诉必须填写理由」
驳回(有理由)    → rejected          仍 frozen，user.status=0
重新申诉        → appealing          覆盖旧理由
受理            → accepted + unfrozen  user.status=1
已解封再申诉    → 400「没有被冻结的账号」
```

### 坑
1. **`updateById` 不会把字段置 NULL**：重提申诉时 `setAppealHandleTime(null)` 被 MyBatis-Plus
   的 `updateStrategy=NOT_NULL` 直接跳过 —— 结果"状态回到申诉中，但处理时间还留着上次的"。
   必须用 `LambdaUpdateWrapper.set(field, null)` 显式置空。
2. **`/api/v1/sso/freeze-appeal` 要手动加白名单**（见上）。
3. **表格列多了「原因」会被压成竖排单字**：没给 width 的弹性列在列数增加后会被挤到几十像素。
   给 width: 200 + `scroll.x` 从 1160 调到 1280。

### 验证
- 登录页：入口存在 → 表单渲染（2 字段 + textarea）→ 空提交报「请输入正确的 11 位手机号」→ 返回登录正常，0 console error
- 运营端：筛选「申诉中」1 条、申诉列显示理由、弹窗 5 个字段 + 受理/驳回，取消不改状态
- 审计：`uc.freeze` / `uc.appeal.submit`（记在用户自己日志里）/ `uc.appeal.accept`
- 收尾：受理后 farmer 恢复 `status=1`，记录留作历史（unfrozen/accepted）
- 发布 `user-center-ops@20261029-uc-ops-r12`、`sso@20261029-sso-r2`

### 已知边界
- **申诉接口未做频率限制**：知道手机号的人可代为提交（最多产生一条待处理申诉，不会解封、不泄露内容）。接公网前应补限流。

## 修复：主数据管理登录后卡在统一认证（无限打转）

### 现象
用户反馈"账号登录后一直在统一认证登录中间页面不跳转"。网关 access.log 里是
每秒 4~6 条 `GET /authorize?` 302 + `GET /sso/callback` 200 交替，**且全程没有 `/api/v1/sso/token`**。

### 根因（agri-master-data/web/src/main.ts）
`bootstrap().finally()` 里先 `app.mount()` 再判断"当前路由是不是公开页"，但**没有 `await router.isReady()`**。
此时 `router.currentRoute` 还是 START_LOCATION（`meta` 为空、`fullPath='/'`），于是：

- 任何页面（**包括公开的 `/sso/callback`**）都被判成受保护页 → `replace('/login?redirect=/')`
- 登录页 `onMounted` 又自动 `redirectToSso()` → 认证中心 302 → 回 callback → 又被踢走 → 死循环

因为是竞态（router 恰好先 resolve 时正常），表现为"有时候能进、有时候卡住"。
`/sso/token` 从未被调用就是证据：callback 组件还没来得及换票，页面就被换掉了。

### 修复
1. **`main.ts`：`await router.isReady()` 之后再判断**（根因）。
2. **`utils/sso.ts` 加防打转冷却**：自动跳转记时间戳，8 秒内再次自动跳直接抛错，
   把控制权交回用户；`redirectToSso(returnTo, { manual })` 区分手动/自动，换票成功清除标记。

### ⚠️ 用户端 `/user/login` 是假登录（待修）
`views/userportal/UserLogin.vue` 里硬编码：
