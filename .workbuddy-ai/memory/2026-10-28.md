## 需求与决策

## 签名与防盗链（最容易踩坑的地方）
nginx 侧（`ops/gateway/conf/conf.d/41-info-service.conf`，**8104/8113/8114 三处必须逐字一致**）：
```nginx
location /vod/ {
    root .;
    secure_link $arg_s,$arg_e;                                  # 顺序：签名在前，过期时间在后
    secure_link_md5 "$secure_link_expires$uri agri-vod-dev-secret";
    if ($secure_link = "")  { return 403; }
    if ($secure_link = "0") { return 410; }
}
```
- **坑 1**：`secure_link $arg_e,$arg_s` 写反 → 一律 403。参数顺序是「签名,过期时间」。
- **坑 2**：签名是 `base64url(md5(原文))` 的**原始 16 字节摘要**，不是 md5 的十六进制串。
  原文 = `<过期秒级时间戳><URI><空格><密钥>`。
- **坑 3**：`nginx.conf` 的 `types` 里原本**没有 mp4**，`default_type application/octet-stream`
  会让视频以错误 MIME 返回，小程序 `<video>` 与部分浏览器内核直接不播。已补 mp4/m4v/mov/webm/m3u8/ts。
- 签名**不绑 IP**：移动端 4G/WiFi 切换会换出口 IP，绑了会让用户"走着走着突然 403"。
- 过期返回 **410 而不是 403**，播放器据此区分"地址过期"（可换票续播）与"无权限"。
- 上传体积：8113 单独给 `/api/v1/info/ops/media/` 放 `client_max_body_size 2048m` + `proxy_request_buffering off`。

## 后端实现
- `com.agri.info.media.VodProperties`（`agri.info.vod.*`）/ `VodSigner` / `MediaStorageService`
- `VodSigner.toUri()` 做前缀去重，允许库里手工填过 `/vod/xxx` 而不拼出 `/vod//vod/xxx`

  - 文件名强制 ASCII（`lesson-20261028-153012-a1b2.mp4`）。**中文文件名会让 nginx 的 `$uri`（已解码）

- 用户端接口（`InfoController`）：
  - `GET /courses` 覆盖 progress 为**按 owner 计算的个人进度**，并补 `enrolled` / `lessonCount` / `totalDurationSec`

- `syncCourseDuration()`：章节增删后把「N 节 / X 小时」写回 info_course.duration，避免列表页对不上。
- `InfoExceptionHandler` 补 `MethodArgumentTypeMismatchException → 400`（原来非法参数落到兜底变 500）。

## 缺陷修复：自主上传的视频播放不了（HEVC 编码）

### 现象
运营端上传视频成功、章节也保存了、签名地址 200 + video/mp4 + 文件大小正确，
但播放器**黑屏**：进度条能走、时长显示正常、**控制台零报错**。

### 根因
上传的是**手机直拍的 H.265 / HEVC**（`hvc1`）。浏览器与小程序的 `<video>` 解不了 HEVC，
但**不会触发 error** —— 实测对比：

| 视频 | readyState | videoWidth | errorCode |
|---|---|---|---|
| HEVC | 4（数据齐） | **0** | **null** |
| H.264 | 4 | 4500 | null |

`canPlayType('video/mp4; codecs="hvc1..."')` 返回空串。
**判据是 `videoWidth === 0`，不是 `video.error`** —— 这是本次最关键的一条。

### 修复（三层）
1. **服务端**：新增 `media/Mp4CodecInspector`（无第三方依赖，自己走 box 结构找
   `moov>trak>mdia>minf>stbl>stsd` 的 sample entry 四字符码）。
   `MediaStorageService` 改为「先写临时文件 → 校验编码 → 通过才 move 到正式目录」，
   不通过直接删临时文件，不会在 vod 目录里留一堆黑屏文件。
   只对 mp4/m4v/mov 检测；webm 的 VP8/VP9 三端都能放，m3u8 是文本清单，都不查。
2. **运营端**：`probeVideo()` 在上传**前**用本地 video 元素预解一遍，
   `videoWidth === 0` 就立刻拦下（否则用户要等几分钟传完才知道白传）。
   同时用它替代原来的 `readDuration`，一次加载同时拿到「能不能播 + 时长」。
3. **已有文件**：用 ffmpeg 把用户已上传的那个转成 H.264 并原地替换（文件名不变，
   数据库 video_url 不用改），原文件备份为 `.hevc-backup.mp4`。

### 坑
- **不能取第一个 `trak`**：mp4 里音频轨可以排在视频轨前面，那样会读到音频编码 `mp4a`，
  把正常的 H.264 视频误判成"不支持"。必须按 `hdlr` 的 handler_type == `vide` 定位视频轨。
  （第一版就是这么写错的，被 `l01.mp4` 测出来。）
- 转码命令要带 `-pix_fmt yuv420p`（否则某些播放器不认 yuv444/10bit）和
  `-movflags +faststart`（moov 前置，边下边播）。
- H.264 体积比 HEVC 大（本例 1.1M → 3.1M），正常现象。
- 获取 ffmpeg：`pip install --user imageio-ffmpeg` 最省事，自带 win64 二进制，
  不用 winget/choco，也不污染项目目录。

### 验证
- 上传 HEVC → 400「视频编码是 H.265 / HEVC…」+ 转码命令
- 上传 H.264 → 200，`codec=H.264`
- 转码后的用户文件 → 浏览器 `videoWidth=720 / videoHeight=1280 / currentTime=2.46 / paused=false`
- 临时文件无残留（`uploading-` 前缀目录已清空）
- 运营端发布 `info-ops@20261028-info-ops-r5`

### 运营须知（要写进使用文档）
- 课程视频统一 **mp4 + H.264(avc1) + AAC**，手机直拍默认多是 HEVC，需先转码。
- 转码命令：`ffmpeg -i 原文件 -c:v libx264 -profile:v high -crf 23 -pix_fmt yuv420p -c:a aac -movflags +faststart 输出.mp4`

## 架构改造：供需大厅接入交易撮合（消除重复造轮子）

### 改造前的重复（四个轮子）
| 能力 | 信息资讯（info_supply_demand 那套） | 交易撮合 |
|---|---|---|
| 供应 | 自建表，**匹配分是 `70 + hash(标题) % 25` 的假值** | agri_trade_product，SKU/库存/审核齐全 |
| 需求 | 同表 sd_type=demand | agri_trade_demand，配送/质量/认证要求 |
| 撮合 | info_sd_match 静态表，分值是建表时写死的 | agri_trade_match_record + 品类/价格/距离/质量四维真算法 |
| 沟通 | info_sd_message | agri_trade_negotiation + 询价报价 |

### 定下的架构：一个数据源，两个入口
```
信息资讯前端(8104/8114) → /api/v1/info/supply-demands（契约不变）
      → agri-info BFF（字段映射 + 联系方式） → agri-trade(8089) 唯一数据源
      → 卖家中心/买家中心读同一份
```
前端**一行没改**，只换后端实现。

### 三道坎（用户拍板）
1. **经营主体**：trade 发布必须有 merchant 绑定 → 演示环境 29 个用户全是 FARMER 且**全部已绑定**，主链路天然通；
   自助建主体接口现成（`POST /api/v1/sso/account/businesses`），后续兜底用。
2. **权限**：`FARMER` 角色的 permissions 里**本来就有** `trade:read/trade:write` + `info:consumer`，无需额外授权。
3. **审核**：trade 商品默认 pending（`product.publish-requires-audit=true`）→ 按来源放行，
   `X-Agri-Source: info` 直接 published，交易模块自身发布仍走审核。

### 改动清单
**agri-trade（3 处）**
- `SellerProductController.create`：新增 `X-Agri-Source` 头；来源=info 时免审 + 免图片
- `validate(request, skus, requireImage)`：图片要求按来源放宽（供需表单没有图片位）
- `replaceImages`：**urls 为 null 时要挡掉**，否则清完旧图立刻 NPE → 整笔发布 500
- `DemandController.createDemand`：返回 `ApiResponse<Demand>`（原来返回 true，拿不到 id，无法存联系方式）

**agri-info（新增 3 个类 + 改 2 个）**
- `integration/TradeClient`：RestTemplate，透传用户 Authorization（不换服务账号，主体归属仍按真实用户）
- `integration/SupplyDemandService`：字段双向映射、品类名→categoryId 缓存、发布后跑一次真匹配回填"预估匹配度"
- `schema.sql` 新增 `info_sd_contact`（trade_type+trade_id 唯一）：**只补联系方式**，不复制主数据
- `InfoController` 六个供需接口改调 SupplyDemandService；`application.yml` 加 `agri.info.trade.*`
- 联系方式为什么要单独存：交易平台按规范不公开电话（走洽谈流程），而信息撮合需要摆在明面上，这是业务差异

### 坑
- **跨库字符串比较的 collation**：agri_trade 是 `utf8mb4_unicode_ci`、agri_info 是 `utf8mb4_0900_ai_ci`，
  `JOIN ... ON p.product_code = CONCAT('MIG', d.sd_no)` 报 `Illegal mix of collations`，要给一侧加 `COLLATE`。
- **UriComponentsBuilder.build() 不编码查询参数**：中文 keyword 以原始字节进 URL，Tomcat 按 RFC 7230 拒成 400
  （日志里是 `keyword=0xc10xaa0xb6…`）。必须 `builder.encode(UTF_8).build().toUri()`。
- **单位解析**：`SUBSTRING_INDEX(...,' ',-1)` 取到的是"斤）"，不是"吨"。改用
  `REGEXP_SUBSTR(..., '[^0-9.,()（） ]+')`，**全角括号必须显式排除**。
- `info_supply_demand.quantity` 是"20 吨（40,000 斤）"这种带千分位和括号的自由文本，
  trade 是 `DECIMAL + unit` 两列，迁移必须解析。
- 前端发布成功页依赖 `{sdNo, status, matchScore, message}`，只返回 id 会显示 "undefined%"。
- 列表的 `matchScore` 现在是 0（trade 公开 VO 不带该字段），前端 PC/移动端都是
  `matchScore > 0` / `v-if="matchScore"` 才渲染，不会显示 0%，无需改前端。

### 存量迁移
6 条供应 → agri_trade_product（product_code 前缀 `MIG`），4 条需求 → agri_trade_demand，
10 条联系方式 → info_sd_contact。旧表 `info_supply_demand` 保留只读作回滚。

## 续：供需大厅「在线沟通」接入交易模块洽谈

### 为什么只接供应侧
交易模块的会话模型是 `agri_trade_negotiation`：唯一键 `(buyer_user_id, seller_id)`，
语义是「买家 ↔ 供应商（按商品）」，open 时还要校验 `requireSeller(sellerId)` 且商品 published。
需求侧的需求方是**采购主体**（merchant），没有对应的反向会话，硬套会把买卖双方角色写反。
所以：**供应详情 → 真实洽谈；需求详情 → 保留 info_sd_message 本地留言**。

### 评估：官网「资讯门户」与「产业资讯」是否重叠/可合并

**结论：不合并，但命名要改。**

对比（评估时的事实）：
| 维度 | 资讯门户 `#/info` | 产业资讯 `#/info/news` |
|---|---|---|
| 内容 | 行情速览 + 头条资讯(5) + 供需快讯 + 学习服务(培训/专家/报告) | 仅文章列表 |
| 资讯部分 | 运营推荐优先的 5 条 | 全量 + 频道筛选 + 分页 |
| 能力 | 聚合导航 | 检索浏览 |

- 重叠**仅限"都展示文章"**这一层：首页放的是"运营精选 5 条"，列表页是"全量 + 可筛可搜可翻页"。
  这是标准的「首页聚合 + 频道细分」结构，合并会让首页过载或让列表页丢掉行情/供需/培训入口。
- **真问题是命名**：官网本身叫"门户"，里面又有一个"资讯门户"，用户会以为是两个门户；
  而且「资讯门户」「产业资讯」并列在顶层导航，看不出是父子关系。
- 改动：
  1. 导航「资讯门户」→ **「资讯」**（`PortalLayout.NAV_ITEMS` + `InfoHome` 的 pageMeta 同步）
  2. 产业资讯列表页顶部加 **「‹ 返回资讯首页」**，把父子层级摆到界面上
  3. 产业资讯补**频道内搜索**（后端 `articles` 早就支持 `keyword`，但页面一直没有入口）：
     受控 input + 回车/按钮触发 + 「清除「xxx」」，实测搜"大蒜"从 8 条降到 2 条
- 发布 `portal@20261028-portal-navmerge-r10`。
- 如果后续仍要合并，正确方向是「InfoNews 吸收 InfoHome 做成带侧栏的资讯主页」，
  而不是把列表塞进首页 —— 但那会牺牲首页对其他频道（行情/供需/培训）的引流作用。

### 续：门户 SEO 基础配置（robots + JSON-LD）
**决策：不改路由。** history 路由改造会波及所有既有 `#/xxx` 链接（收藏、外链、其他模块跳转），
且本地无法验证收录效果，风险与收益不匹配。改为做低风险、**在 hash 路由下仍有效**的部分。

- **不做 sitemap**：`/portal/#/info/news/1` 这种带 `#` 的地址会被搜索引擎规范化掉，
  写进 sitemap 是无效声明。已在 `robots.txt` 里写明原因，避免后人误以为漏了。
- `public/robots.txt`：Allow all + 注释说明 SPA 的收录限制。发布后需**手动复制到
  `ops/gateway/bucket/portal/robots.txt`**（publish 的版本目录在 `versions/<v>/` 下，
  爬虫访问的是 `/portal/robots.txt`，不会去版本目录找）。
- `utils.ts` 新增 `applyStructuredData(id, data)` / `useStructuredData`：
  用**固定 id 覆盖**而不是追加 —— SPA 切页面不卸载 head，追加会让数据越堆越多。
- 注入内容：
  - 资讯首页 `ld-site`：WebSite + SearchAction（指向 `#/info/search?keyword={keyword}`）
  - 资讯详情 `ld-article`：NewsArticle（headline / description / datePublished / articleSection /

### 修复 3：供需 id 撞号导致串页（前端）

→ `sdMatches(id, type)` 支持透传；`SupplyDemandDetailPage` 从路由 query 读 type；

## 白屏事故：Git Bash 把 --base 当路径转换，发布脚本的守卫又用错了判断方式

**现象**：发布 prod@20261028-monitor 后，所有页面白屏。控制台报
`Failed to load module script: Expected a JavaScript-or-Wasm module script but the server responded with a MIME type of "text/html"`。
index.html 里的资源引用变成：
`/Program Files/WorkBuddyAI/resources/vendor/PortableGit/prod/versions/20261028-monitor/assets/...`

**根因（两层）**
1. Git Bash / MSYS2 会把以 `/` 开头的命令行参数做**路径转换**。
   `npx vite build --base=/prod/versions/x/` 里的 `/prod/...` 被转成
   `C:/Program Files/.../PortableGit/prod/...`，直接写进了产物。
2. `ops/gateway/scripts/publish.mjs` 的白屏守卫用的是

   于是守卫放行。守卫存在但形同虚设。

- 构建时加 `MSYS_NO_PATHCONV=1 MSYS2_ARG_CONV_EXCL='*'`

  要求**每一个**都以 `/{app}/versions/{version}/` 开头（`badUrls.length > 0` 即失败），
  并在报错里提示 MSYS_NO_PATHCONV 这个坑
- 重新发布 `prod@20261028-monitor-r2`（当前指针）
- ⚠️ 坏版本 `20261028-monitor` 仍在 bucket 里（版本目录不可变），**不要回滚到它**；
  上一个可用版本是 `20261027-tianditu-key-r2`

  → **finally 里把状态还原回 pending**（演示库不能因为跑 e2e 被改）

### 又一个命名不一致（记下来）
个人实名的"通过"在库里落 **`verified`**，企业资质落 **`approved`**。
两个接口的字段名也不同（`certStatus` vs `status`）。凡是跨这两个列表做统计的地方都要归一。

## 用户中心第十三轮：跨模块入口（我的服务）

### 关键设计
1. **只声明"模块需要什么"，不替模块做权限判断**。`requires` 里只放本服务真能判定的四项
   （merchant / merchant_verified / personal_verified / business_identity），判不了一律写空数组。

3. 入口新标签打开，不把用户中心冲掉。
4. 目录是静态事实、状态是实时算的 —— 所以不需要表。

### 验证方法（这轮的重点）

- **独立推导比对**：用 `/summary` + `/identity-applications` 另算一遍四个前置条件，

- **入口不是死链**：6 个 entryUrl 逐个发请求断言 200。
- **状态会跟着数据变**：临时提交并审核通过一个业务身份 → 交易撮合 `blocked→available`、

- e2e 里 `call()` 忘了支持 body，POST 发成空体 → 后端 400「请求体不能为空」，

  否则正常响应被当失败、页面一直空表。

  `/api/` 兜底 → core-platform 返回 **HTTP 200 + body.code=500**（不是 404，很难查）。
  `72-portal.conf` 里那条只在 :8098 生效。已按同一口径补上，并加 `X-Served-By` 便于排查。
- `my-merchants` 返回的 `merchantId` 是字符串，`agri_trade_order.buyerId` 是数字，
  比较前要统一成 String。

## 用户中心第十七轮：二次验证（TOTP）—— 用户端 29/29 收官

### 交付
- **迁移 V50**：`platform_user_mfa`（`secret_cipher` / `status` / `recovery_codes` / `last_used_step`）
- **后端**：`TotpService`（RFC 6238）、`MfaCrypto`（AES-GCM）、`MfaService`、
  `SsoAccountController` 的 `/mfa*` 端点、登录闸门 + `/login-standalone-mfa`
- **前端**：`pages/account/Mfa.tsx`（门户）、`agri-sso/frontend` 登录页第二因子步骤
- navModel **28/29 → 29/29（全部落地）**，发布 `portal@20261028-uc-mfa-r16`、`sso@20261028-sso-mfa-r18`
- 验证脚本 `scripts/e2e-uc-mfa.mjs`（44 项断言，TOTP 在脚本侧独立计算）

### 关键设计
1. **两段式启用**（pending → confirm → active）：扫码后必须输一次正确的码才启用。
   直接 active 会把"装错 App / 手机时间不准"的人锁在门外。
2. **真的拦在登录上**：密码/短信通过后**不建会话**，只发 5 分钟一次性 challenge（Redis）。
   第二步用 challenge 换 userId，**不接受前端自报用户 id**（否则改个 id 就绕过密码）。
3. challenge 一次性，**校验失败也立即消费** —— 失败只能重走密码登录，防暴力试码。
4. 密钥存 AES-GCM 密文；注释里明说"配置里的默认密钥等于没加密，只是防数据库单点泄露"。
5. 备用码 8 个、一次性、用掉即移除；停用要再验一次码，且清空密钥（不留"停了密文还在"）。
6. 已 active 时禁止重新 setup —— 否则拿到会话的人可以悄悄换密钥把机主锁死。

### 踩坑
- **备用码哈希不一致**：生成时按 `ABCDE-FGHIJ`（带连字符）哈希，校验时先 `replaceAll("[\\s-]","")`
  再去哈希 → 永远匹配不上，表现为"备用码登录 401、停用也失败"。修法：统一用
  `normalizeRecovery()` 归一化后再哈希。
- **重放保护过严**：停用/重生成备用码复用了登录的 `verifyCode`（带 `lastUsedStep` 拦截），
  导致"刚登录完立刻停用"直接 400。拆出 `verifyForAction`（忽略重放）—— 这类动作成功后码就失效了，
  再拦重放只会让用户以为功能坏了。
- **lambda 参数遮蔽**：`.map(code -> sha256(normalizeRecovery(code)))` 与外层参数 `code` 同名 → 编译报错。
- **检查脚本断言会过期**：`check-uc-account-center.mjs` 原来断言"未接入项要显示缺口说明"，
  29/29 之后这条必然失败。已改成**反向断言**（侧栏不应再有「待接入」），以后谁改回 pending 就报警。
- `e2e-uc-authz` 解绑只置 unbound 留痕，测试行会一直堆在库里；已补 SQL 按 marker 整行删除。

### 已知缺口（页面已写明，不夸大）
二次验证只拦在独立登录接口。**子系统跳转的 OIDC 授权码流程尚未接入第二因子** ——
需要在授权码流程里插入可恢复的中间态（保存 authorize 参数、验证后继续签码），
改动面大于本轮范围，留作下一步。
