# 主数据企业端 · 组织与权限：数据边界与重叠检查

日期：2026-10-30　范围：组织架构 / 部门与岗位 / 成员账号 / 邀请成员 / 角色与权限

## 一、结论：哪些能力归谁

| 能力 | 权威源 | 主数据企业端角色 | 是否重复 |
|---|---|---|---|
| 账号 / 成员归属 | **core-platform**（`platform_user` + `platform_user_merchant`） | 只读展示 | 原来重复，已收敛 |
| 加入申请 / 邀请审批 | **core-platform**（`platform_merchant_join_request` + 审批） | 审批入口 | 原来缺入口，已在 core 补接口 |
| 组织 / 部门 / 岗位 | **agri-masterdata**（`agri_md_organization/department/position`） | 可维护（新增/编辑） | 无重叠 |
| 业务角色 | **agri-masterdata**（`agri_md_role`） | 可维护（新增/编辑） | 与平台角色分离 |

## 二、查出的重叠（已处理）

### 1. 两套成员数据，数量不一致
- 主数据本地 `agri_md_user`：主体 2001 有 **5 条**（`seed_2001_*`，种子数据）
- 用户中心 `platform_user_merchant`：主体 2001 只有 **2 条**（真实绑定）

原「成员账号」页读本地表，等于把种子数据当成员展示。
**处理**：成员页改读用户中心成员接口，本地表只用于补"部门/岗位"，匹配不上显示"未分配"。
不删除本地表（组织架构里的部门归属仍需要它），但**不再作为成员列表的依据**。

### 2. "邀请成员"没有可落库的实现
主数据后端没有邀请表、也没有签发/接受接口；原页面是诚实的说明页（不造假表单），但完全不能操作。
用户中心有完整的「申请加入 → 负责人审批 → 创建绑定」闭环，**缺的只是"负责人看待审批列表"接口**。
**处理**：在 core 补 `GET /businesses/{id}/join-requests`，邀请页改为"待审批申请 + 审批"，
审批通过由 core 写 `platform_user_merchant`。**不新建邀请表**。

## 三、查出的冲突（已修）

### 1. 客户详情跨主体越权（上一轮已修，此处记录）
`CustomerServiceImpl.getById` 无归属校验，主体 2001 能读 T1001 的客户。列表有过滤、详情没有。

### 2. 部门/岗位的关联字段类型不一致
- `agri_md_department.dept_id` 是 **varchar**（业务编码 `DEPT-2001-01`），真正主键是自增 `id`
- `agri_md_position.dept_id` 是 **bigint**，指向的是 `department.id`

`Department` 实体的 `@TableId` 指向 `dept_id`（varchar），按实体主键 `selectById` 永远查不到部门。
**处理**：企业端按 `id` 查询并校验归属，注释里写明两表同名列语义不同。

### 3. 岗位表新旧双列，只填新列插入失败
`agri_md_position` 同时有 `pos_code/pos_name`（NOT NULL、唯一）与 `position_code/position_name`。
实体只映射新列 → `Field 'pos_code' doesn't have a default value`。
**处理**：实体补旧列映射，写入时两套列同值。

## 七、成员任职档案（`agri_md_member_profile`）

### 为什么单独建表，而不是给 `agri_md_user` 加列

| 障碍 | 说明 |
|---|---|
| `password` NOT NULL | 给一个 SSO 账号建本地档案就得填个假密码，把"认证凭证"和"员工档案"混在一起 |
| `username` 全局唯一 | 同一账号可以在多个主体任职，一条本地档案装不下 |
| 已有 5 条种子数据 | 加列会让它们看起来像真员工，与"成员以用户中心为准"直接冲突 |

新表只存 **「账号 ID → 组织位置」**，不冗余用户名/手机号（账号改名后这里不会过期）：

```
agri_md_member_profile
  tenant_id         主体（服务端强制，取请求头 X-Agri-Merchant）
  platform_user_id  统一认证账号 ID（platform_user.id）
  org_id / dept_id / position_id   组织 / 部门 / 岗位
  job_status        active / left
  UNIQUE (tenant_id, platform_user_id)
```

三个位置字段统一 **VARCHAR**：三张表主键类型各不相同（`organization.id` 雪花 Long、
`department.id` 自增 BIGINT、`position.position_id` 雪花 VARCHAR），存字符串就不用来回转换。

### 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/user/member-profiles` | 本主体全部任职档案（含 orgName/deptName/positionName） |
| PUT | `/api/user/member-profiles/{platformUserId}` | upsert，三字段至少一项 |
| DELETE | `/api/user/member-profiles/{platformUserId}` | 清除任职 |

### 信任边界（重要）

主数据库看不到认证库的 `platform_user_merchant`，**无法校验 platformUserId 是否真属于本主体**。
靠三层兜住：

1. 记录按 tenant 隔离，不同主体各存一份；
2. 组织/部门/岗位必须属于本主体（逐一校验）—— 这条最要紧；
3. 展示时**以用户中心成员列表为主表左连接**，孤儿记录（账号已离开主体）显示不出来。

即使塞一个伪造的 platformUserId，最多给自己主体留一条显示不出来的空记录。

### 两个额外的校验

- **三项全空直接拒绝**：否则前端漏传字段就会静默把人的部门岗位抹掉，接口还返回成功。
  清空是 DELETE 的语义。
- **岗位必须属于所选部门**：不然会出现"在质检部任职、岗位却属于仓储部"这种自相矛盾的档案。

### 验证

`scripts/e2e-mdm-member-profile.mjs`（28 项断言）：成员数以用户中心为准（2 人，≠ 本地 5）、
页面分配 → 直连 MySQL 核对 tenant/org/dept/position/job_status、页面回显名称、
换部门后是更新不是新增（upsert）、孤儿记录不撑大成员数但接口仍返回、
跨主体组织被拒（3002）、三项全空被拒（1004）、岗位部门不匹配被拒（1004）、
页面清除后库里归零。
