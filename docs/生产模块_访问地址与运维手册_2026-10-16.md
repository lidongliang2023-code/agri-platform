## 三、前端版本与发布

- 发布形态：`ops/gateway/bucket/prod/` 下"**版本目录 + 指针**"——`prod/index.html` 与 `prod/manifest.json` 指向 `prod/versions/<版本>/`。
- 当前线上版本记录在 `ops/gateway/bucket/prod/manifest.json` 的 `version` 字段（本文当日为 `20261016-v2`）。
- **发布用脚本，不要手敲**：
  ```bash
  node ops/deploy-prod-frontend.mjs --version=20261016-v3   # 构建(带 base) + 发布 + 发布后巡检
  node ops/deploy-prod-frontend.mjs --dry-run               # 只算版本号、打印步骤
  ```
  脚本内置两道防线：构建产物若不含 `/prod/versions/<版本>/` 前缀即中止（漏带 `base` 会让产物按根路径拼 chunk，表现为"页面能开、一堆 MIME 报错"）；发布后巡检白屏/未捕获异常/console 错误超基线则自动回滚指针。
- 手工回滚：把 `prod/versions/<上一版本>/index.html` 覆盖到 `prod/index.html`，并把 `manifest.json` 的 `version` 改回上一版本。

## 六、还不是"生产地址"

## 六之前：为什么 `:8180` 只做跳转（2026-10-16 实测教训）

平台的 SSO 客户端注册表（`core-platform/core-app/src/main/resources/application-dev.yml`，
`agri.sso.clients.prod`）是一份 **redirect_uri 前缀白名单**，当前登记的是：

```
http://localhost/        # 只覆盖 :80，不含带端口的地址（前缀匹配，注释里写明了）
http://127.0.0.1/
http://localhost:8190/   # 运营端独立入口，当年开 :8190 时加的
http://127.0.0.1:8190/
http://localhost:5173/   # dev server
http://prod.agri.local/
```

`:8180` 不在其中 → 直接在该端口跑应用时，SPA 把 SSO 回调拼成 `http://localhost:8180/sso/callback`，
认证中心判「redirect_uri 不在白名单」，登录页开不出来（页面直接显示一段 JSON）。
把 :8180 加进白名单需要"改配置 → 重建 → 重启 core-platform"，代价高于收益，
所以 :8180 改成**整站 302 到 :80**：应用与 SSO 回调都落在白名单覆盖的 :80 上，深链原样保留。
若将来确实要让 :8180 自己承载应用，按上面那段做（白名单加两条 → 重建重启平台 → 网关换回本地服务写法）。

上面全是**本机地址**。网关配置为这个模块预留的正式域名是 `prod.agri-platform.com`（本地另挂了 `prod.agri.local`）。要变成公网可访问，还需要：域名解析/hosts、TLS 证书、把 nginx 与后端部署到目标服务器 —— 这些不在当前这台机器的部署范围内，需要目标环境信息后才能做。

## 七、一键启动整套（2026-10-16 补：重开机后实测过一次）

本机这套东西**没有**做成 Windows 服务（Redis 有服务注册但当前会话起不动），
重开机后要按依赖顺序手动拉起。用一条命令即可（幂等：已在跑的组件自动跳过）：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\ops\local\start-production-stack.ps1
```

顺序与依赖：**MySQL(3306) → Redis(6379) → core-platform(8093) → agri-trade(8089)
→ agri-masterdata(8083) → agri-production(8092) → nginx(80/8080/8086/8090/8098/8180/8190)**。

### 7.1 这次部署踩到并写进脚本的四个坑

1. **MySQL 不是服务**：要用 `my.ini` 启动，而 `--defaults-file` 的路径带空格，
   **必须整段用引号包住**，否则 mysqld 把路径截断在空格处，报
   `Failed to open required defaults file: C:\ProgramData\MySQL\MySQL`（看着像配置丢了，其实只是参数被切开）。
2. **Redis 服务起不动**（`Cannot open 'Redis' service`）：改为直接跑
   `C:\Redis\redis-server.exe C:\Redis\redis.windows.conf`。
3. **core-platform 的库口令默认是 `root123`**（`application.yml` 的 `${MYSQL_PASSWORD:root123}`），
   而本机 MySQL 的 root 口令是 `root` —— 不带 `MYSQL_PASSWORD=root` 启动会直接失败：
   `Access denied for user 'root'@'localhost' (using password: YES)`。
   **这条最容易被误判成"数据库挂了"**：库其实好好的，只是口令没对上。
4. **nginx 必须用 ASCII 联接点**（仓库路径含中文与括号），且 Windows 版 nginx 是控制台程序
   —— 不脱离式启动会**占住当前终端**（这次实测把一条会话挂了几分钟），脚本里用 `Start-Process` 脱离。

### 7.2 脚本自身的一个编码坑（写给后来改它的人）

`.ps1` 必须带 **UTF-8 BOM**：Windows PowerShell 5.1 对无 BOM 的文件按 ANSI（本机是 GBK）读，
里面的中文注释会变成乱码并**把字符串引号撑破**，表现为一堆 `Missing closing '}'` /
`The string is missing the terminator` —— 看着像语法错，其实是编码。

### 7.14 用户 / 企业注册与认证审核闭环（2026-10-20）

- 登录：<http://localhost/production/login>（经统一认证中心）。
- 注册：<http://localhost:8090/register>（企业会员 / 个人会员两套表单）。
- 认证审核：<http://localhost:8080/user/audit>（主数据运营端「用户管理 → 认证审核」）。
- 登录页按原型只保留「手机号 + 验证码 / 账号 + 密码」两种方式，不再要求手动选择会员身份；
  后端按账号绑定主体自动识别。
- 注册页按原型改为可分步返回的三步向导：1 注册账号 → 2 创建主体 → 3 认证开通；
  每步单独校验，最后一步确认资料并提交审核。
- 分步接口已真实拆分：
  - `POST /api/v1/sso/register-account`：只创建账号与 FARMER 角色；
  - `GET /api/v1/sso/onboarding/status`：按 SSO 会话恢复当前步骤；
  - `POST /api/v1/sso/onboarding/subject`：创建主体与认证草稿；
  - `POST /api/v1/sso/onboarding/certification`：把草稿激活为待审核并返还子系统回跳。
- 登录接口返回 `stage`：未建主体自动进入第 2 步，未提交认证进入第 3 步，
  待审核显示审核中，已通过才按原授权码回跳业务系统；历史无 member_type 的主体按已完成处理。
- 直接打开 `http://localhost:8090/login` 时不再要求子系统授权上下文：账号密码走
  `/api/v1/sso/login-standalone`，手机验证码走 `/api/v1/sso/login-standalone-by-sms`；
  按钮始终可点击，已认证用户分别跳转生产用户端 / 运营端，未完成用户按阶段进入注册向导。
- 登录页、注册页左上角「返回首页」统一进入官网门户
  <http://localhost:8098/portal/#/>，不再回到认证中心根页或业务回调页。
- 个人会员注册必须填写真实姓名和身份证号；身份证只在请求中出现一次，服务端保存掩码与加盐摘要。
- 企业会员注册保存企业名称、统一社会信用代码、行业、规模、地址、联系人与登录密码，并生成
  pending 主体认证申请。
- 注册会同时落库：`platform_user`、`platform_user_role`、`platform_merchant`、
  `platform_user_merchant`；企业另写 `platform_merchant_certification`，个人另写
  `platform_user_identity`。
- 审核通过后：企业申请变为 `approved`，主体 `verify_status=approved` 并写审核时间；
  个人实名变为 `verified`，同时同步个人主体 `verify_status=approved`。
- `GET /api/v1/platform/merchants/mine` 现在返回 `memberType/verifyStatus/verifyTime`，
  子系统可直接判断认证是否生效。
- 已用真实页面完成个人、企业注册并登录回跳；测试账号：
  `19900002004 / Test12345`（个人）、`19900002005 / Test12345`（企业），均已审核通过。
- 发布版本：统一认证 **20261020-sso17**、主数据 **20261021-m14**、core-platform 本轮 jar。
