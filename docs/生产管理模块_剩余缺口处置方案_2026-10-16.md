## 二、growth（8 条）—— 本轮已定口径

**欠账**：`prod_growth_record` 只有 height / leaf_count / pest_level，而页面要 `growthLevel`（长势评级 1~4）、
`leafAreaIndex`（叶面积指数）、`pestInfo`（病虫害描述）；环境数据页面要宽表（空气温湿度/土壤温湿度/光照/CO₂/降雨），
本地 `agri_prod_sensor_data` 是**长表**（一行一个 sensor_type/value/unit）。

**口径（本条代拍，可否决）**：

1. 新建 `agri_prod_growth_record`，**按页面契约建列**：除 height(→plantHeight)、leaf_count、growth_stage、
   record_date、weather、recorder_id、remark 外，**直接加** `growth_level tinyint`、`leaf_area_index decimal(6,2)`、
   `pest_info varchar(200)`。**不**让这三列长期靠推算。
2. 演示数据：`growth_level` 按固定规则由株高/叶数/病虫害等级推（`pest_level>=2` → 2 偏弱；`pest_level=1` 或叶数
   偏少 → 3 正常；其余 → 4 旺盛），`leaf_area_index` = 叶数 ÷ 10（保留 1 位），`pest_info` 取 remark 中已有的病害描述
   （无则 NULL）。**种子脚本里把"推算"写进注释**，上线后这三列由人工录入。
3. 环境数据：**不新增宽表**，在服务层把长表**透视**成页面字段（`temperature→airTemperature`、
   `humidity→airHumidity`、`soil_temperature→soilTemperature`、`soil_moisture→soilMoisture`、
   `illuminance→illuminance`、`co2→co2`、`rainfall→rainfall`），按 `plot_id + data_time` 分桶；
   没有的传感器类型一律 null（不编）。演示补一批 `humidity / soil_moisture / illuminance` 读数（1 个地块 × 若干时点）。
   `environment/history` 取同一批数据按天聚合（min/avg/max），`overview` 出该地块的记录数/最近生育期/最近病虫害等级。
4. 端点：`GET /growth/records`(分页) `POST /growth/records` `PUT /growth/records/{id}` `GET /growth/environment`(分页)
   `GET /growth/environment/history` `GET /growth/by-plot?plotId=`(裸数组) `GET /growth/pest?level=`(裸数组)
   `GET /growth/overview?plotId=`；网关把 `growth` 加进通用切流正则。

**其他遗留**：平台演示数据的生育期用词（花期/果期/成熟期/分蘖期/抽穗期）与页面下拉
（苗期/开花期/结果期/采收期）不一致，导致总览页「生育期分布」把这些记录都归到「未记录」、

改法（改数据还是改页面词表）属产品口径，未擅自动手。

**与文档原文的三处差异（都写进了代码注释）**：

1. 订阅表的列名按**页面契约**：`period`（daily/weekly/monthly/quarterly）+ `receivers`（JSON 数组，可多人），
   而不是文档写的 `frequency(WEEKLY/MONTHLY)` / `receiver`（单数）。按文档那两个名字建列会立刻静默失真：
   daily/quarterly 无处安放、多个接收人只存得下第一个。
2. 报表表在文档列之外补了 4 列：`period`（周期标签，页面要显示）、`summary_json`（聚合快照本体）、
   `file_size`（页面要显示文件大小）、`download_key`（导出文件要被 `window.open` 打开，
   而这个动作用不了 Authorization 头 —— 用报表自带的一次性令牌，而不是把会话令牌拼进 URL）。
   文档给的 `period_start/period_end` 保留：由`类型 + 页面传入的日期`推导（日报=当天、周报=自然周、
   月报=自然月、季报=季度、年报=自然年）。
3. 报表**落库即「已完成」**（`status=2`）：这一版是即时聚合快照，不是异步任务 ——
   做成异步要配任务表与轮询，而本模块连消息通道都没有；与其做一个"永远转圈"的假异步，不如让数据立刻可用。

**本部署确实没有数据源的项（一律留空，不填看起来合理的数）**：

- **亩均生产成本**：投入品没有单价列、采收批次没有金额列 → 看板上该卡片恒为「—」，
  页面顶部会显式列出「暂无数据源的指标：亩均生产成本」（这是页面自己的 missingFields 提示，不是我们编的）。
  计划表上确有 `total_budget` / `expected_output`，但那是**计划预算与预期产值**，不是实际成本/产值。
- **投入产出比**：同因，`/dimension` 的 `inputCost` / `outputValue` 恒为 null。
  ⚠️ 页面对这两个字段直接做算术（`outputValue / Math.max(1, inputCost)`），会显示 `NaN`——
  这是页面缺少"无数据源"分支所致（前端遗留，未改前端源码）。
- **生成人**：本服务拿不到平台用户档案（平台没有 `/auth/me` 之类端点，主体绑定信息里只有 userId），
  报表 `generated_by` 留空、CSV 里写「未接入」。页面在该列为空时显示「系统自动」（页面侧兜底文案）。

**演示数据**：3 份报表（生产月报·2026-06 / 生产周报·2026-W22 / 生产日报·2026-10-13）
是**调真实的 `POST /analytics/reports` 生成**的（不是手写 INSERT），快照与 CSV 都是演示数据的真实聚合
（例：月报 2026-06 = 采收批次 1 / 采收量 1250 kg / 已出结论检测 2 条中合格 1 条 / 未处理告警 3 条）。
订阅基线**留空**，原因见下面的前端遗留第 ①：只要列表里有订阅行，页面就会挂出"仅保存在本浏览器、
未同步服务端"的横幅 —— 那句话在服务端已实现之后是**错的**，与其让演示页面挂一条错话，不如留空态。

**前端遗留（不改前端源码，只记录）**：

1. 订阅卡片顶部横幅文案过期：条件是 `subscriptions.length > 0`，文案写死"仅保存在本浏览器
   （localStorage），未同步服务端" —— 订阅端点已实现后，这半句不再成立（"不会真的推送"这半句仍然成立）。
2. 启停订阅（开关）只改浏览器本地状态，**不回写服务端**：页面上把订阅关掉之后，服务端行仍是启用态。
3. 生成人为空时页面显示「系统自动」（页面兜底文案），以及上面的 `NaN` 问题。

## 四、iot（10 条）

**欠账**：绑定关系、指令下发、保养记录三张表都不存在；且下发指令没有真实通道。

**口径**：

1. 建三张表：`agri_prod_iot_binding`（device_id ↔ plot_id，含绑定时间/解绑时间/状态）、
   `agri_prod_iot_command`（命令类型、参数 JSON、下发时间、回执状态、回执内容）、
   `agri_prod_iot_maintenance`（保养类型、执行人、日期、内容、下次保养日期）。
2. `POST /iot/devices/{id}/commands` **只记录指令**（status=ISSUED），**不做真实下发**；响应里带
   `delivery: "record-only"`，页面提示"已记录（本部署未接下发通道）"。**这是本条的关键决定**：
   宁可显示"未接通道"，也不做一个点了没反应的假按钮。
3. `readings/latest`、`readings/series` 直接复用 `agri_prod_sensor_data`（长表透视，同 growth 的映射函数——
   两个模块共用一份透视工具，别写两遍）。

### 状态：✅ 已完成（2026-10-16，单段单提交）

**实测数字**：probe 该段缺口 **10 → 0**（总缺口 29 → 19；另 10 条是"没有页面调用的 api 函数"发出的路径，

实体列 0 处不一致；页面巡检 4 条路由 0 白屏 / 0 console 错误，看图核对：设备列表 5 台（按当前农场筛）、
绑定管理 8 条已绑定（含采集指标与频率）、设备详情 36 条真实读数与曲线。

**落地**：新表 `agri_prod_iot_binding` / `agri_prod_iot_command` / `agri_prod_iot_maintenance`；
`IotOpsController` + `IIotOpsService`/实现 + 4 个出参 VO + 3 个 mapper；
`ISensorPivotService` 扩了 `latest` / `series`（与 growth 共用同一份长表透视与指标别名）；

**切流前必须先补的两件事（不补就是"切完了、页面是空的"）**：

1. **设备端点返回页面契约**。`/iot/devices` 原先直接把实体丢给前端，而页面读 `deviceId / onlineStatus /
   lastHeartbeatAt` —— 实体里这三个字段都没有：页面上表现为"行 id 是 undefined（详情链接拼成 /undefined）、
   每台设备都显示离线、最后上报永远是"-""，而接口是 200。现已返回 `IotDeviceVO`（含 `plotId`，
   供页面查地块名）。**这类问题只有把前端接上来才看得见，probe/diff 两个脚本都照不出来。**
2. **设备主数据**：本服务设备表原先只有 3 台本地演示设备，平台侧演示集有 10 台。本轮把 10 台按新增的
   `platform_device_id` 列迁过来（与农场表的 `platform_farm_id` 同法），并补 `plot_ref` 承载页面口径的
   地块标识（设备列表的"关联地块"列与按地块筛选都靠它）。**不迁的话切流会把设备列表从 10 台切成 3 台。**

**本轮定的关键口径（与方案文档原文的差异，都写进了代码注释）**：

1. **指令只记录、不真下发**：状态固定 `ISSUED`、回执写明"未实际送达"、响应带 `delivery=record-only`。
   平台侧旧实现是"按设备在线状态判终态"（在线→SUCCESS、离线→FAILED）——本部署没有下发通道，
   写 SUCCESS 等于谎报"指令已送达"。页面按 status 渲染 Tag 时显示原样文案（`COMMAND_STATUS_META`
   没有 ISSUED 时会显示原始值），需要页面配合把这一档展示得更清楚。
2. **绑定表的列按页面契约**（binding_id / device_id / device_code / device_name / bind_type /
   bind_target_id / bind_target_name / metrics / frequency / status / bound_at，另加 unbound_at），
   而不是文档的"device_id ↔ plot_id"。页面的 `bindType` 有 PLOT / GREENHOUSE / FARM 三种，
   只建 plot_id 会让大棚/农场绑定无处安放。
3. **`{id}` 路径变量限定数字**（`{id:\d+}`）：平台侧还有 `/iot/devices/offline` 这类字面量路径，
   被 `/devices/{id}` 吃掉会变成 400，而网关的 404 回退接不住 400（20-prod.conf 里记过这一类坑）。
   顺带把 `POST /iot/devices` 的空体 500 改成 400（设备名称是 NOT NULL 列，不校验就插会 500）。

**演示数据与探测副作用**：绑定/指令/维修三张表的演示行由 agri_core 同名表机械转换，
**排除了探针空体写入的垃圾行**（device_id 形如 DEVC2026…/DEV-B1/DEV-TEST-01/TEST-ONLINE-*，共 40 行）；
device_id 一律按 platform_device_id 换算成本地主键（子查询取不到就报错，不静默少插）。
探针会打 `POST /iot/devices/1/heartbeat`，跑完必须复位设备的心跳/状态（复位脚本见交付说明）。

**仍未收敛的（随第六轮一起做）**：绑定对象中的地块标识（`bind_target_id`）与设备的 `plot_ref` 仍是
平台侧标识（DEMO-PLOT-xxx）——地块主数据收敛后要一并回填成本地主键；本地两台设备（DEV001/002）
在设备列表里的"关联地块"因此显示成本地主键数字（如 `1`），不是名称。

## 五、ai（10 条）

**欠账**：本部署没有任何模型依赖；病虫害识别与产量预测没有可依据的实现。

**口径**：

1. 会话与消息（`GET/POST /ai/assistant/sessions`、`PATCH /sessions/{id}`、`GET/POST /ai/assistant/messages`）
   **要做**：建 `agri_prod_ai_session` / `agri_prod_ai_message`，助手回复走**规则式应答**（基于本服务已有数据的

### 9.1 联调脚本 `scripts/e2e-farm-create.mjs`（新增）

链路：真浏览器 → 网关 :80 → agri-production :8092 → MySQL。**走真实表单**
（填 farmName/省市区/面积/负责人/电话 → 点「保存并查看详情」），断言 16 项：
列表页已登录、POST 返回 id 字符串、跳转 id 与接口返回一致、详情页回显名称/面积/负责人/电话/省市区/资质、
列表关键字能搜到、全链路无 4xx/5xx。实测 **16/16 通过**（农场 id=203）。

两个"看起来对、其实错"的坑，写进脚本注释避免后人重踩：

1. **页面里裸 fetch 一定 401**。访问令牌只在 `store/auth` 内存里、由 axios 请求拦截器注入
   `Authorization`；手写 fetch 不经过拦截器 → 后端按「登录已过期」返回 **HTTP 200 + code 401**
   （不进 4xx 统计，极易被漏看）。第一版脚本就是这么写的，8 项断言里 7 项挂在这上面。
   正解是驱动真 UI，让应用自己的请求带上令牌。
2. **登录态怎么给**：先落同源静态文件（`/prod/manifest.json`）→ 页面上下文 POST `/api/v1/auth/login`
   （`credentials: include`，刷新令牌进 HttpOnly Cookie）→ `evaluateOnNewDocument` 写**非凭证界面态**
   （`agri_user_info`/`agri_roles`/`agri_permissions`/`agri_market_id`）。少写界面态，应用会认为"没登录过"
   而跳过启动续签，表现为全程 401。

### 9.4 探针脚本两处修复（本文件第七节"剩余缺口"的收口）

**① `GET /settings/logs` 假阳性 —— 病根不在 URL 解析，在响应体匹配。**

前面两轮都在改 `settings.ts` 的调用解析，都没修掉。真正原因：`/settings/logs` 返回的是
**操作日志数据**，而日志行里本身就有 message 为「接口不存在」的历史记录（探针自己早先打 404 留下的），
于是这条**健康**端点的响应体里含有该子串，被 `body.includes('接口不存在')` 判成"缺处理器" ——
**探针把自己的历史痕迹当成了证据**。现改为只认结构化字段：HTTP 404，或响应包装体的 `message` 字段含该字样；
响应体不是 JSON（网关文本页）时才退回全文匹配。

> 顺手别把 `code === 404` 也加进去：业务码 404 是"**记录**不存在"（如 `/admin/approvals/1/approve`
> 的审批单 1 不存在），与"**端点**没有处理器"是两码事 —— 实测加进去缺口会从 0 虚增到 27 条。

实测：**缺口 1 → 0，成功 136 → 137**（`/settings/logs` 归位），退出码 0。
另外把缺口头条的 HTTP 状态一并打出来，省得下次再靠重放猜。

**② 令牌过期时会打出"缺口 0"的假象。**

令牌过期 → 每条请求都回 401/403 → 全被归到"有处理器但本次调用未成功"，于是缺口显示 0。
（上一轮就据此误判过一次，261 条 403。）现在跑前解 JWT 的 `exp`：已过期直接退出码 2 并给出换令牌的命令，
剩不到 5 分钟只警告；非 JWT 令牌跳过检查。实测伪造过期令牌 → 退出码 2、提示"已于 2023-11-15 过期"。
