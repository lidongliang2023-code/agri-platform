# 生产管理模块 · 剩余 45 条缺口的处置方案（2026-10-16）

> 背景：用户端/运营端已按段切到 agri-production（缺口 90+ → 45）。剩余 45 条**不是"把代码搬过来"**，
> 每条背后都欠一个数据模型或产品口径决定。本文把这些决定一次性定下来（**由我按建议代拍，可被否决**），
> 并给出每段的落地清单，之后一段一轮执行，不再重复侦察。

## 一、全局约定（沿用既有纪律）

- 表结构：本服务约定 = 自增主键 + 业务编号（`xxx_id`）+ `tenant_id varchar(191)` + `create_time/update_time` + `deleted bigint`。
- 演示数据：从 `agri_core` 的演示行**机械转换**（脚本生成、不用手抄），排除探针留下的空体写入垃圾行。
- 每段做完的判据：① probe 该段缺口 0（或按口径显式豁免）② `diff-cutover-regressions` 无新增项
  ③ 页面巡检 0 白屏 0 console 错误 + 截图人工核对 ④ `verify.mjs` 15 通过 / 0 失败 + 实体列 0 处不一致
  ⑤ 演示基线复位 ⑥ 提交信息里写实测数字与遗留。
- 平台域不实现：租户/市场主体、平台角色权限、告警规则（详见 probe 的 `PLATFORM_OWNED_PATHS`）。

## 二、growth（8 条）—— 本轮已定口径

**欠账**：`prod_growth_record` 只有 height / leaf_count / pest_level，而页面要 `growthLevel`（长势评级 1~4）、
`leafAreaIndex`（叶面积指数）、`pestInfo`（病虫害描述）；环境数据页面要宽表（空气温湿度/土壤温湿度/光照/CO₂/降雨），
本地 `agri_prod_sensor_data` 是**长表**（一行一个 sensor_type/value/unit）。

**口径（本条代拍，可否决）**：

1. 新建 `agri_prod_growth_record`，**按页面契约建列**：除 height(→plantHeight)、leaf_count、growth_stage、
   record_date、weather、recorder_id、remark 外，**直接加** `growth_level tinyint`、`leaf_area_index decimal(6,2)`、
   `pest_info varchar(200)`。**不**让这三列长期靠推算。
2. 演示数据：`growth_level` 按固定规则由株高/叶数/病虫害等级推（`pest_level>=2` → 2 偏弱；`pest_level=1` 或叶数
   偏少 → 3 正常；其余 → 4 旺盛），`leaf_area_index` = 叶数 ÷ 10（保留 1 位），`pest_info` 取 remark 中已有的病害描述
   （无则 NULL）。**种子脚本里把"推算"写进注释**，上线后这三列由人工录入。
3. 环境数据：**不新增宽表**，在服务层把长表**透视**成页面字段（`temperature→airTemperature`、
   `humidity→airHumidity`、`soil_temperature→soilTemperature`、`soil_moisture→soilMoisture`、
   `illuminance→illuminance`、`co2→co2`、`rainfall→rainfall`），按 `plot_id + data_time` 分桶；
   没有的传感器类型一律 null（不编）。演示补一批 `humidity / soil_moisture / illuminance` 读数（1 个地块 × 若干时点）。
   `environment/history` 取同一批数据按天聚合（min/avg/max），`overview` 出该地块的记录数/最近生育期/最近病虫害等级。
4. 端点：`GET /growth/records`(分页) `POST /growth/records` `PUT /growth/records/{id}` `GET /growth/environment`(分页)
   `GET /growth/environment/history` `GET /growth/by-plot?plotId=`(裸数组) `GET /growth/pest?level=`(裸数组)
   `GET /growth/overview?plotId=`；网关把 `growth` 加进通用切流正则。

## 三、analytics（8 条）

**欠账**：报表中心（生成/导出/订阅）没有表，也没有"报表是什么"的定义。

**口径**：

1. `agri_prod_report`（report_id、report_name、report_type、period_start/period_end、status、file_url、
   generated_at、generated_by、remark）；`agri_prod_report_subscription`（subscribe_id、report_type、
   frequency(WEEKLY/MONTHLY)、channels(JSON)、receiver、status）。
2. `POST /analytics/reports` = **即时聚合落库快照**（不是异步任务）：按 type+period 从已有表（tasks/harvests/
   inputs/quality）聚合出一份 JSON 摘要存进 report 行，`file_url` 指向 `/analytics/reports/{id}/export` 生成的 CSV；
   导出**先落 CSV 文件到 `target/exports/`**并以静态路径返回（不引入对象存储）。
3. `GET /analytics/dashboard`、`/dimension`、`/trend` 为纯聚合（无新表），维度沿用页面给的字段口径。
4. 订阅：`POST /reports/subscribe` 落订阅行；`GET /reports/subscriptions` 列表。**不写真投递**（没有消息通道），
   在返回体里明确 `delivery: "not-configured"`，避免"订阅了但永远收不到"却看不出来。

## 四、iot（10 条）

**欠账**：绑定关系、指令下发、保养记录三张表都不存在；且下发指令没有真实通道。

**口径**：

1. 建三张表：`agri_prod_iot_binding`（device_id ↔ plot_id，含绑定时间/解绑时间/状态）、
   `agri_prod_iot_command`（命令类型、参数 JSON、下发时间、回执状态、回执内容）、
   `agri_prod_iot_maintenance`（保养类型、执行人、日期、内容、下次保养日期）。
2. `POST /iot/devices/{id}/commands` **只记录指令**（status=ISSUED），**不做真实下发**；响应里带
   `delivery: "record-only"`，页面提示"已记录（本部署未接下发通道）"。**这是本条的关键决定**：
   宁可显示"未接通道"，也不做一个点了没反应的假按钮。
3. `readings/latest`、`readings/series` 直接复用 `agri_prod_sensor_data`（长表透视，同 growth 的映射函数——
   两个模块共用一份透视工具，别写两遍）。

## 五、ai（10 条）

**欠账**：本部署没有任何模型依赖；病虫害识别与产量预测没有可依据的实现。

**口径**：

1. 会话与消息（`GET/POST /ai/assistant/sessions`、`PATCH /sessions/{id}`、`GET/POST /ai/assistant/messages`）
   **要做**：建 `agri_prod_ai_session` / `agri_prod_ai_message`，助手回复走**规则式应答**（基于本服务已有数据的
   检索式回答，如"某地块最近一次土壤检测""本月采收量"），并在响应里标注 `engine: "rule-based"`。
2. 病虫害识别（`POST /ai/pest-detection`）与产量预测（`GET/POST /ai/yield-forecast`）：
   **暂不实现**，保持缺口并在文档中标为"待产品定模型口径"。理由：没有模型就是编结果，
   而预测类数字一旦被当真会直接影响生产决策。若产品决定"走经验规则"，再按规则实现并标注 `engine: "rule-based"`。

## 六、farms / plots（8 条）—— 需要单独一轮的重构

**欠账**：农场主数据有两份（平台库 `prod_farm_info` 与本库 `agri_prod_farm_info`，靠 `platform_farm_id` 映射），
两边的 list/detail 仍在平台侧；而 certs（资质证照）、soil（土壤检测）两组数据也各存一份。

**口径（分两步，不可跳步）**：

1. **第一步：收敛主数据**。把 `/farms`、`/plots` 的 list/detail/create/update/delete 全段切到本服务，
   同时把 `agri_prod_plot_info` 补 `platform_plot_id` 映射（与 farm 同法），并迁移：
   farm certs（core 44 行）→ 新表 `agri_prod_farm_cert`；plot soil（core 44 行）→ 已有表
   `agri_prod_soil_record`（需先把列口径对齐到页面：`ph/organicMatter/nitrogen/phosphorus/potassium/moisture/tester`）。
2. **第二步**：切 `farms`/`plots` 段（含 `/{id}/certs`、`/{id}/soil`、`/{id}/summary`、`/{id}/status`），
   并同步更新 `FarmIdResolver` 与所有引用 farm_id 的段（tasks/plans/harvests/quality/alerts/messages/members）
   的映射断言。
3. 风险提示：这是本次迁移里唯一会**同时改动已上线段**的动作，必须单独一轮、单独提交，且切前对
   "按农场筛选"的每个页面做一次逐一回归（这正是前几轮踩过坑的地方：筛选静默失效）。

## 七、settings/logs（1 条）
