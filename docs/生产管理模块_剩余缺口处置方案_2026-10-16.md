## 二、growth（8 条）—— 本轮已定口径

**欠账**：`prod_growth_record` 只有 height / leaf_count / pest_level，而页面要 `growthLevel`（长势评级 1~4）、
`leafAreaIndex`（叶面积指数）、`pestInfo`（病虫害描述）；环境数据页面要宽表（空气温湿度/土壤温湿度/光照/CO₂/降雨），
本地 `agri_prod_sensor_data` 是**长表**（一行一个 sensor_type/value/unit）。

**口径（本条代拍，可否决）**：

1. 新建 `agri_prod_growth_record`，**按页面契约建列**：除 height(→plantHeight)、leaf_count、growth_stage、
   record_date、weather、recorder_id、remark 外，**直接加** `growth_level tinyint`、`leaf_area_index decimal(6,2)`、
   `pest_info varchar(200)`。**不**让这三列长期靠推算。
2. 演示数据：`growth_level` 按固定规则由株高/叶数/病虫害等级推（`pest_level>=2` → 2 偏弱；`pest_level=1` 或叶数
   偏少 → 3 正常；其余 → 4 旺盛），`leaf_area_index` = 叶数 ÷ 10（保留 1 位），`pest_info` 取 remark 中已有的病害描述
   （无则 NULL）。**种子脚本里把"推算"写进注释**，上线后这三列由人工录入。
3. 环境数据：**不新增宽表**，在服务层把长表**透视**成页面字段（`temperature→airTemperature`、
   `humidity→airHumidity`、`soil_temperature→soilTemperature`、`soil_moisture→soilMoisture`、
   `illuminance→illuminance`、`co2→co2`、`rainfall→rainfall`），按 `plot_id + data_time` 分桶；
   没有的传感器类型一律 null（不编）。演示补一批 `humidity / soil_moisture / illuminance` 读数（1 个地块 × 若干时点）。
   `environment/history` 取同一批数据按天聚合（min/avg/max），`overview` 出该地块的记录数/最近生育期/最近病虫害等级。
4. 端点：`GET /growth/records`(分页) `POST /growth/records` `PUT /growth/records/{id}` `GET /growth/environment`(分页)
   `GET /growth/environment/history` `GET /growth/by-plot?plotId=`(裸数组) `GET /growth/pest?level=`(裸数组)
   `GET /growth/overview?plotId=`；网关把 `growth` 加进通用切流正则。

（苗期/开花期/结果期/采收期）不一致，导致总览页「生育期分布」把这些记录都归到「未记录」、

**与文档原文的三处差异（都写进了代码注释）**：

1. 订阅表的列名按**页面契约**：`period`（daily/weekly/monthly/quarterly）+ `receivers`（JSON 数组，可多人），

   daily/quarterly 无处安放、多个接收人只存得下第一个。
2. 报表表在文档列之外补了 4 列：`period`（周期标签，页面要显示）、`summary_json`（聚合快照本体）、
   `file_size`（页面要显示文件大小）、`download_key`（导出文件要被 `window.open` 打开，

   文档给的 `period_start/period_end` 保留：由`类型 + 页面传入的日期`推导（日报=当天、周报=自然周、
   月报=自然月、季报=季度、年报=自然年）。
3. 报表**落库即「已完成」**（`status=2`）：这一版是即时聚合快照，不是异步任务 ——
   做成异步要配任务表与轮询，而本模块连消息通道都没有；与其做一个"永远转圈"的假异步，不如让数据立刻可用。

**本部署确实没有数据源的项（一律留空，不填看起来合理的数）**：

- **亩均生产成本**：投入品没有单价列、采收批次没有金额列 → 看板上该卡片恒为「—」，
  页面顶部会显式列出「暂无数据源的指标：亩均生产成本」（这是页面自己的 missingFields 提示，不是我们编的）。
  计划表上确有 `total_budget` / `expected_output`，但那是**计划预算与预期产值**，不是实际成本/产值。
- **投入产出比**：同因，`/dimension` 的 `inputCost` / `outputValue` 恒为 null。
  ⚠️ 页面对这两个字段直接做算术（`outputValue / Math.max(1, inputCost)`），会显示 `NaN`——
  这是页面缺少"无数据源"分支所致（前端遗留，未改前端源码）。
- **生成人**：本服务拿不到平台用户档案（平台没有 `/auth/me` 之类端点，主体绑定信息里只有 userId），
  报表 `generated_by` 留空、CSV 里写「未接入」。页面在该列为空时显示「系统自动」（页面侧兜底文案）。

**演示数据**：3 份报表（生产月报·2026-06 / 生产周报·2026-W22 / 生产日报·2026-10-13）
是**调真实的 `POST /analytics/reports` 生成**的（不是手写 INSERT），快照与 CSV 都是演示数据的真实聚合
（例：月报 2026-06 = 采收批次 1 / 采收量 1250 kg / 已出结论检测 2 条中合格 1 条 / 未处理告警 3 条）。
订阅基线**留空**，原因见下面的前端遗留第 ①：只要列表里有订阅行，页面就会挂出"仅保存在本浏览器、

**前端遗留（不改前端源码，只记录）**：

1. 订阅卡片顶部横幅文案过期：条件是 `subscriptions.length > 0`，文案写死"仅保存在本浏览器
   （localStorage），未同步服务端" —— 订阅端点已实现后，这半句不再成立（"不会真的推送"这半句仍然成立）。
2. 启停订阅（开关）只改浏览器本地状态，**不回写服务端**：页面上把订阅关掉之后，服务端行仍是启用态。
3. 生成人为空时页面显示「系统自动」（页面兜底文案），以及上面的 `NaN` 问题。

## 四、iot（10 条）

**欠账**：绑定关系、指令下发、保养记录三张表都不存在；且下发指令没有真实通道。

**口径**：

1. 建三张表：`agri_prod_iot_binding`（device_id ↔ plot_id，含绑定时间/解绑时间/状态）、
   `agri_prod_iot_command`（命令类型、参数 JSON、下发时间、回执状态、回执内容）、
   `agri_prod_iot_maintenance`（保养类型、执行人、日期、内容、下次保养日期）。
2. `POST /iot/devices/{id}/commands` **只记录指令**（status=ISSUED），**不做真实下发**；响应里带
   `delivery: "record-only"`，页面提示"已记录（本部署未接下发通道）"。**这是本条的关键决定**：
   宁可显示"未接通道"，也不做一个点了没反应的假按钮。
3. `readings/latest`、`readings/series` 直接复用 `agri_prod_sensor_data`（长表透视，同 growth 的映射函数——
   两个模块共用一份透视工具，别写两遍）。

### 状态：✅ 已完成（2026-10-16，单段单提交）

**实测数字**：probe 该段缺口 **10 → 0**（总缺口 29 → 19；另 10 条是"没有页面调用的 api 函数"发出的路径，

实体列 0 处不一致；页面巡检 4 条路由 0 白屏 / 0 console 错误，看图核对：设备列表 5 台（按当前农场筛）、
绑定管理 8 条已绑定（含采集指标与频率）、设备详情 36 条真实读数与曲线。

**落地**：新表 `agri_prod_iot_binding` / `agri_prod_iot_command` / `agri_prod_iot_maintenance`；
`IotOpsController` + `IIotOpsService`/实现 + 4 个出参 VO + 3 个 mapper；

**切流前必须先补的两件事（不补就是"切完了、页面是空的"）**：

1. **设备端点返回页面契约**。`/iot/devices` 原先直接把实体丢给前端，而页面读 `deviceId / onlineStatus /
   lastHeartbeatAt` —— 实体里这三个字段都没有：页面上表现为"行 id 是 undefined（详情链接拼成 /undefined）、
   每台设备都显示离线、最后上报永远是"-""，而接口是 200。现已返回 `IotDeviceVO`（含 `plotId`，
   供页面查地块名）。**这类问题只有把前端接上来才看得见，probe/diff 两个脚本都照不出来。**
2. **设备主数据**：本服务设备表原先只有 3 台本地演示设备，平台侧演示集有 10 台。本轮把 10 台按新增的
   `platform_device_id` 列迁过来（与农场表的 `platform_farm_id` 同法），并补 `plot_ref` 承载页面口径的
   地块标识（设备列表的"关联地块"列与按地块筛选都靠它）。**不迁的话切流会把设备列表从 10 台切成 3 台。**

**本轮定的关键口径（与方案文档原文的差异，都写进了代码注释）**：

1. **指令只记录、不真下发**：状态固定 `ISSUED`、回执写明"未实际送达"、响应带 `delivery=record-only`。
   平台侧旧实现是"按设备在线状态判终态"（在线→SUCCESS、离线→FAILED）——本部署没有下发通道，
   写 SUCCESS 等于谎报"指令已送达"。页面按 status 渲染 Tag 时显示原样文案（`COMMAND_STATUS_META`
   没有 ISSUED 时会显示原始值），需要页面配合把这一档展示得更清楚。
2. **绑定表的列按页面契约**（binding_id / device_id / device_code / device_name / bind_type /
   bind_target_id / bind_target_name / metrics / frequency / status / bound_at，另加 unbound_at），
   而不是文档的"device_id ↔ plot_id"。页面的 `bindType` 有 PLOT / GREENHOUSE / FARM 三种，
   只建 plot_id 会让大棚/农场绑定无处安放。
3. **`{id}` 路径变量限定数字**（`{id:\d+}`）：平台侧还有 `/iot/devices/offline` 这类字面量路径，
   被 `/devices/{id}` 吃掉会变成 400，而网关的 404 回退接不住 400（20-prod.conf 里记过这一类坑）。
   顺带把 `POST /iot/devices` 的空体 500 改成 400（设备名称是 NOT NULL 列，不校验就插会 500）。

**演示数据与探测副作用**：绑定/指令/维修三张表的演示行由 agri_core 同名表机械转换，
**排除了探针空体写入的垃圾行**（device_id 形如 DEVC2026…/DEV-B1/DEV-TEST-01/TEST-ONLINE-*，共 40 行）；
device_id 一律按 platform_device_id 换算成本地主键（子查询取不到就报错，不静默少插）。
探针会打 `POST /iot/devices/1/heartbeat`，跑完必须复位设备的心跳/状态（复位脚本见交付说明）。

**仍未收敛的（随第六轮一起做）**：绑定对象中的地块标识（`bind_target_id`）与设备的 `plot_ref` 仍是
平台侧标识（DEMO-PLOT-xxx）——地块主数据收敛后要一并回填成本地主键；本地两台设备（DEV001/002）
在设备列表里的"关联地块"因此显示成本地主键数字（如 `1`），不是名称。

## 五、ai（10 条）

**欠账**：本部署没有任何模型依赖；病虫害识别与产量预测没有可依据的实现。

**口径**：

1. 会话与消息（`GET/POST /ai/assistant/sessions`、`PATCH /sessions/{id}`、`GET/POST /ai/assistant/messages`）
   **要做**：建 `agri_prod_ai_session` / `agri_prod_ai_message`，助手回复走**规则式应答**（基于本服务已有数据的

### 9.4 探针脚本两处修复（本文件第七节"剩余缺口"的收口）

**① `GET /settings/logs` 假阳性 —— 病根不在 URL 解析，在响应体匹配。**

另外把缺口头条的 HTTP 状态一并打出来，省得下次再靠重放猜。

**② 令牌过期时会打出"缺口 0"的假象。**

令牌过期 → 每条请求都回 401/403 → 全被归到"有处理器但本次调用未成功"，于是缺口显示 0。

## 十五、作物升级为主数据（2026-10-16，用户口径）

### 15.1 落位决策：放在 agri-production，不放 agri_masterdata

动手前确认过：`agri_masterdata` 里只有租户类型 / 单位 / 认证状态这类**平台级**字典，
而生产域的其它台账（农场、地块、团队成员）**都在 agri_production**、都由本服务自己维护。

### 15.2 做了什么

**建表**（`schema-mysql.sql` 加入，启动时 `CREATE TABLE IF NOT EXISTS` 自动建）：
`agri_prod_crop_info` —— 租户级主数据，字段：
`crop_code`（同租户内唯一）、`crop_name`、`crop_category`、`growth_cycle_days`、

> ① `crop_code` 的唯一索引建在 **(tenant_id, crop_code)** 而不是全局 —— 编码是租户自己的编号空间；
> ② `crop_name` **不建唯一索引**，改在服务层按"未删除行里不重名"校验 ——
> 逻辑删除不参与唯一索引，软删过的同名作物会把新行挡死（`plan_code` 上踩过这个坑）。

## 十六、地块也关联作物主数据（2026-10-16，"继续下一步"取的是这条）

### 16.1 现状：地块从来没有"当前作物"的入口

动手前先查清了地块侧的真实情况：

### 17.2 顺带修掉一个真缺陷：作物编码会撞已软删的行

原因在上一轮我自己写的 `generateCode`：它按"当前行数 + 1"编号，而

修法：新增 `CropInfoMapper.maxCropCodeSeq`（**原生 SQL**，绕开逻辑删除过滤）取
"已用过的最大序号 + 1"；并给插入加一层 `DuplicateKeyException` 重试，
把并发撞码的可能性收在服务里、不抛 500 给用户。

## 十八、作物主数据改由运营端维护（2026-10-16，产品口径变更）

**产品口径**：`作物主数据放在生产管理模块，由运营端维护。`

### 18.1 权限：用平台自带的 RBAC，而不是自己造角色判断

动手前先把权限落点摸清了。生产服务**已经接了平台的 RBAC 组件**
（`agri-common` 的 `com.agri.common.rbac`：`platform.rbac.operator-paths` 覆盖
`/api/v1/production/admin/**`，`read/write-permission = production:read / production:write`），
而且 `@OperatorOnly` 这个注解**就是为"运营动作挂在业务路径上"设计的**（它的注释原文就写了这一点）。

所以没有另造一套：作物写接口（新增 / 修改 / 启停 / 删除）挂 `@OperatorOnly`，
默认要求 `production:write`；读接口（分页 / options / categories）保持开放。

> 权限码为什么是 `production:write` 而不是 `produce:write`：平台的 `platform_role` 表里
> **FARMER 角色也持有 `produce:read/produce:write`**（那是"生产数据"的权限，农户本来就该有）。
> 两个码字面相近、后果相反 —— 这条在 `application.yml` 里也有注释，免得后人想当然合并。

> 我起初写了个自造的 `CallerRoleService`（解令牌里的 `roles` 声明 + 硬编码超管/市场运营），
> 发现平台组件后**删掉了**：自造的判断要自己操心"验签/顺序/角色清单维护"，
> 而平台组件是拿令牌去认证中心实时解析权限码的，口径与运营端其它接口完全一致。

## 十九、地块列表「状态」全显示"未知"（2026-10-16，用户现场反馈）

**现象**：地块管理列表的状态列全是"未知"。

### 19.1 根因：与农场列表同一种错（出参形态 ≠ 页面口径）

- 页面按**数字码**渲染：`PLOT_STATUS_META` = `{0 已停用 / 1 空闲 / 2 在种 / 3 采收期 / 4 休耕}`，
  状态筛选按数字比较、卡片视图按数字上色、详情页按数字出标签；
- 而接口直接序列化了库里的文本：`agri_prod_plot_info.status` 存的是 `active / inactive`
  （只表示"启用 / 停用"这一层），页面拿 `'active'` 去查数字字典 → 三处（列表 / 卡片 / 详情）全"未知"。

> 第 10 节（农场列表状态）是同一个病：**库内文本、页面数字、出参没做换算**。
> 那次修了农场，这次是地块。

### 19.2 处置：出参给数字码，其中"在种"由计划台账定

地块表的状态列**只有"启用 / 停用"两层语义**，页面却要区分"空闲 / 在种" —— 这个区分在本平台有权威口径：

## 二十三、退出登录 / 缺少令牌 → 跳登录页（2026-10-16，用户口径）

**用户口径**：点击退出登录后、或者缺少平台访问令牌时，跳转登录页面。

### 23.1 改前的实际行为（先跑脚本钉住，再改）

新增 `scripts/e2e-auth-redirect.mjs` 把四个场景跑了一遍，改前**四条全失败**：

| 场景 | 改前落点 |
|---|---|
| 用户端点「退出登录」 | `http://localhost/production/dashboard`（**业务页**） |
| 运营端点「退出登录」 | 也是 `/production/dashboard`（**跑错端**） |
| 无会话直接打开 `/production/farms` | 停在 `/production/farms`（**业务页**，页面已经渲染出来） |
| 无会话直接打开 `/admin/production/crops` | 停在业务页 |

两条链路各自的毛病：

1. **退出登录**：清本地态 → `POST /auth/logout`（吊销刷新令牌、清 Cookie）→ 跳
   `{SSO}/logout?client_id=prod`。而统一认证中心的登出**忽略 `redirect_uri`**、
   **写死回跳 `${origin}/?logout=1`**；应用的 `/` 又一律把人送去 `/production/dashboard` ——
   刚登出的人被送回业务页，再被 401 弹走，最后停在**运营端**登录页。
2. **缺少令牌 / 401**：`@/utils/request` 跳的 `/login` 在**没有 `?end=user`** 时分流到
   **运营端**登录页（用户端页面也这样）；而且**没有任何路由守卫** —— 无会话直开业务页会先渲染页面、
   再让一串接口 401，表现为"闪一下空页面"。

### 23.2 改了什么

1. **路由守卫**（`router/index.tsx` 新增 `RequireAuth`）：`/production/**` 与 `/admin/production/**`
   在渲染前先看令牌，没有就**直接**跳**本端**登录页，业务请求一个都不发；
   顺带把"这台浏览器上次在用哪个端"记进 `localStorage.agri_end`。
2. **`/` 识别登出信号**（新增 `RootEntry`）：`?logout=1` 是统一认证中心登出后的固定回跳，
   现在识别它 → 落回**本端**登录页（端取 `agri_end`，默认用户端），不再送去仪表盘；
   其余情况保持原行为（→ 生产数据看板）。
3. **401 按端跳**（`utils/request.ts`）：`/admin/**` → `/admin/login`，其余 → `/production/login`；
   已经在登录页就不再跳（免得打断 SSO 交接页上的"立即跳转 / 改用本地账号"）。
   `/login` 路由保留，兼容旧链接（它的分流规则没动）。

### 23.3 实测（`e2e-auth-redirect.mjs`，改前 4 项全挂 → 改后 4 项全过）

四个场景的最终落点都是**统一认证中心登录页**
`http://localhost:8090/login?client_id=prod&redirect_uri=…%2Fsso%2Fcallback&state=…`：

- 用户端退出登录 ✓（不再落业务页、也不再跑错端）

## 二十七、统一认证中心：手机验证码登录 / 手机号验证码注册落地（2026-10-16，接着上一节）

上一节把「手机号+密码」落地了，这一节把**手机验证码登录**与**手机号验证码注册**也做进去
（微信那两个仍等凭据）。两者都要短信通道，所以先定通道口径。

### 27.1 短信通道：可插拔 + **验证码不回前端**

`agri.auth.sms.mode`：`none`（默认，未配置服务商 → 发送接口**直接拒绝**并说明原因）
/ `dev`（**只在 application-dev.yml 打开**：验证码**只写后端日志**，不回响应体、不以明文落库）
/ 将来接真实服务商时的对应值（补一个 sender 实现即可）。

> 关键取舍：dev 通道**也不把验证码回给前端**。这样页面流程与生产完全一致，
> 不存在"验证码漏给前端"的口子；联调时由脚本从 Redis 取（本机同一台机器），
> 页面只如实提示"验证码已写入后端日志"。这比"为了演示把码显示在页面上"安全得多。

验证码存 Redis：TTL 5 分钟、同一手机号 **60 秒内不重发**、最多验 5 次（错满即作废）、验过即删（防重放）。

### 27.2 接口与注册口径

- `POST /api/v1/sso/sms/code`：{@code {phone, scene}}，scene = `login` / `register`（两场景的码不通用）；
- `POST /api/v1/sso/login-by-sms`：手机号 + 验证码 + 授权上下文 → 建全局会话、签码、回跳；
- `POST /api/v1/sso/register-by-sms`：手机号 + 验证码 + 昵称 → **建账号 + 授 FARMER 角色**，注册成功即登录；
  三个端点都加进了 `JwtAuthFilter` 白名单（它们发生在"拿令牌之前"，不放行会 401 卡死登录流程）。

**注册口径（本实现取的②，需产品确认）**：

① "注册即开通自己的经营主体"（为每个注册者建一家主体）／② **"先注册、等运营开通"**（本实现）。
账号建好但**不建 `platform_user_merchant` 绑定** —— 绑定到哪家主体、什么身份是产品口径；
未绑定账号进业务域会收到**可读的 403**「当前账号还没有绑定经营主体，请联系平台运营在「用户-主体绑定」里配置」，
不是白屏。**不擅自把新用户塞进任何既有主体**（那会让他看到别人的数据）。
另外注册**不设默认口令**（随机 BCrypt 占位）：注册走验证码，密码登录要等用户自己设 ——
实测用任意密码登录该账号回 `5001`。

### 27.3 认证中心页面

四个 Tab：**验证码登录**（含"没有账号？用这个手机号注册"开关，注册成功即登录）、**手机号密码**、
**账号密码**、**微信扫码**（如实说明依赖）。

> 真浏览器联调当场逮到一个页面缺陷：密码输入框原先被写成**无条件渲染**，
> 于是「验证码登录」Tab 上也挂着那个 `required` 输入框 —— 空着提交会被浏览器拦下，
> 表现为**"点了登录什么都不发生"**（接口一次都没发出去）。改成只在两个密码类 Tab 渲染后恢复正常。

## 三十一、投入品模块叫法统一：「投入品类型」vs「流水类型」（2026-10-16，承第三十节）

### 31.1 病灶（复核第三十节第②条的结论）

投入品模块有**两个**容易混的字段，之前在两套名字里打转：

- `inputType` —— 投入品自身的属性（后端 `agri_prod_input_material.material_type`，值域
  SEED / FERTILIZER / PESTICIDE / FEED / VET / OTHER），前端共享常量在 `pages/user/inputs/shared.ts`；
- `flowType` —— 出入库流水动作（`prod_input_stock_flow.flow_type`，1 入库 / 2 领用 / 3 退回 /
  4 盘盈 / 5 盘亏 / 6 报损）。

同一个 `inputType`，改名前**六处叫「分类」、八处叫「类型」**：

| 位置 | 改名前的叫法 | 实际字段 |
| --- | --- | --- |
| InputList 档案列 / 编辑弹窗 / 导入模板说明与表头 / 导出档案表头 | 分类 | `inputType` |
| InputList 筛选标签 / 使用台账列 / 导出台账表头 | 类型 | `inputType` |
| InputStock 库存总览列 | 分类 | `inputType` |
| InputStock **流水列 / 流水筛选 / 盘点弹窗 / 导出流水表头** | **类型** | **`flowType`（另一个字段！）** |
| InputUsages 列 / 导出表头 | 分类 | `inputType` |
| InputDetail 基本信息 / 流水列 | 类型 | 前者 `inputType`、后者 `flowType` |
| Create 新建表单 | 投入品类型（本来就对） | `inputType` |

也就是说：**同一页里两个「类型」指的不是同一件事** —— `InputStock` 的库存表「分类」是投入品类型，
流水表「类型」却是流水动作；`InputDetail` 同样。这是"看页面觉得乱"的一个具体来源，且不涉及数据，
属于零风险可清理项。
